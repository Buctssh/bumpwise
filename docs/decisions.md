# 设计决策记录 (ADR)

记录 Bumpwise 中重要的设计决定: 当时面对什么问题, 选了什么, 为什么, 付出了什么代价.
代码说明了"怎么做", 这份文档说明"为什么这样做". 以后推翻某个决定时, 不删除原来的记录, 而是新增一条, 把旧的标记为"已被 ADR-xxx 取代".

每条记录的结构:

- **背景**: 要解决的问题, 有哪些约束;
- **决定**: 选了什么;
- **理由**: 为什么这样选, 考虑过哪些其他方案;
- **代价**: 这个决定带来的限制, 以及以后什么情况下需要重新考虑.

## ADR-001 不使用 agent 框架

**背景**
LangChain, LangGraph, CrewAI 等框架提供了现成的 agent 循环, 工具调用, 状态管理. Bumpwise 的目标是做 agent 的基础设施 (harness, trace, eval), 而这些恰好是框架替使用者做掉的部分.

**决定**
直接使用模型厂商的 SDK 和 Python 标准库, 不引入 agent 框架. V1 不做多 agent, 不做 RAG.

**理由**

- 项目的核心价值在框架不提供的部分: 工具设计, 权限策略, 运行环境隔离, 验证, 评测. agent 循环本身只有约 200 行, 用框架省不了多少代码;
- 框架会转换消息格式. DeepSeek 返回的 thinking 块带有签名, 必须原样回传 (见 ADR-003), 多一层转换就多一个出错而且难以排查的地方;
- 自己实现, 才清楚每一步为什么这样做. 框架里的概念都能在代码里找到对应: 循环对应 LangGraph 的图和条件边, `max_turns` 对应 `recursion_limit`, 权限策略的 `ask` 对应 `interrupt()`, 事件回调对应 callbacks, V2 的 trace 对应 LangSmith.

**代价**
检查点, 从断点恢复, 人工审批的界面都要自己实现. 如果以后需要多个 agent 按复杂的流程协作, 或者需要持久化的运行状态, 再重新评估.

## ADR-002 纵向切片, 演进式开发

**背景**
完整的系统包括模型接入, 运行环境, 工具, 权限, 循环, trace, 题目, 验证, 评测, 沙箱. 一次性设计好全部, 很容易在没有真实数据的情况下做出错误的抽象.

**决定**
先手工完成两个真实仓库的升级 (V0, 见 `docs/v0/`), 再按版本逐步构建: V1 最小可运行, V2 trace, V3 题目和流水线, V4 验证 (grader), V5 护栏和交给人, V6 评测, V7 经验与记忆, V8 统一接口, V9 沙箱 (V7 是在 V4 时新增的, 见 ADR-016). 每个版本都是能端到端运行的完整系统, 而不是某一层的半成品.
V5 之后的顺序已经调整为: V6 评测框架 → V9 沙箱 → V7 → V8 → 题库和最终评测, 见 ADR-020.
V6 之后又调整为: V7 → 记忆的消融实验 → V8 → 题库和测试 → V9 沙箱, 见 ADR-022.

**理由**

- V0 的手工过程决定了 V1 需要哪些工具 (`docs/v0/procedure.md` 附录 C), 而不是凭想象设计;
- 先让系统跑起来 (walking skeleton), 每个版本根据上一个版本暴露出的问题来改进;
- 有些决定故意推迟, 等有数据再做 (比如 ADR-012).

**代价**
早期的代码以后可能需要重构. 每个模块都有单元测试, 重构的风险是可控的.

## ADR-003 模型接口: 内部统一使用 Anthropic 消息格式

**背景**
不同的模型服务商有不同的接口格式 (Anthropic 格式, OpenAI 格式). 现在使用 DeepSeek, 它同时提供两种兼容接口.

**决定**

- 定义 `LLMClient` 接口, 只有一个方法 `create(system, tools, messages)`, 每种接口格式写一个适配器;
- harness 内部的消息, 工具定义统一使用 Anthropic 格式, 由适配器负责转换;
- 服务商的差异 (密钥, 地址, 默认模型) 写在 `config.py` 的 `PROVIDERS` 表里, 由 `LLM_PROVIDER` 选择.

**理由**

- Anthropic 格式的内容是"块"的列表 (text, thinking, tool_use, tool_result), 表达能力最完整, 从它转换到 OpenAI 格式比反过来容易;
- 模型返回的 thinking 块带有签名, 后续请求必须原样带回, 否则接口会拒绝. 使用 Anthropic 格式, 回复的内容可以直接追加进历史, 不需要任何转换;
- loop 只依赖 `LLMClient` 接口, 测试时可以换成一个按顺序返回固定回复的假模型, 不联网, 不花钱, 结果完全可控.

**代价**
OpenAI 格式的适配器还没有实现, 现在选择 `deepseek-openai` 会明确报错.

## ADR-004 用 Environment 接口隔离运行环境

**背景**
agent 需要执行命令, 读写文件. 现在在本机运行, 以后要在 Docker 容器里运行 (V9).

**决定**
定义 `Environment` 接口: `exec`, `read_bytes`, `write_bytes`, `describe`, `close`. 工具只通过这个接口操作, 不直接调用 `subprocess` 或 `open`. 现在只有 `LocalEnvironment` 一个实现.

**理由**

- 换成 Docker 时, 工具和 loop 的代码都不用改, 只需要新增一个实现;
- 路径检查放在这一层: 所有文件操作都经过 `_resolve`, 越出工作目录的路径 (包括 `..` 和绝对路径) 一律拒绝;
- `describe()` 告诉模型当前的操作系统和 shell, 模型才知道应该写 `cmd.exe` 还是 `/bin/sh` 的语法.

**代价**
路径检查只对文件工具有效, 对 `run_command` 无效 (见[已知的局限](#已知的局限)).

## ADR-005 子进程不继承密钥, 也不能等待输入

**背景**
agent 执行的命令由模型决定. 父进程的环境变量里有模型服务商的密钥; 有些命令会停下来等待键盘输入.

**决定**

- 子进程的环境变量中, 名字包含 `API_KEY`, `TOKEN`, `SECRET`, `PASSWORD` 的一律去掉;
- 标准输入接到 `DEVNULL`, 并设置 `GIT_TERMINAL_PROMPT=0`, `PIP_NO_INPUT=1`;
- 把目标仓库的虚拟环境放到 `PATH` 最前面, 并强制 Python 使用 UTF-8 输出.

**理由**

- 命令的输出会发给模型服务商. 子进程如果能读到密钥, 一条 `set` 或 `env` 命令就会把它泄露出去;
- agent 是一次性执行命令, 只有命令结束后才能看到输出. 命令如果在等待输入, 模型看不到提示, 只能干等到超时. 让读取输入的命令立刻失败, 模型能马上看到报错, 改用 `-y` 这类非交互的参数;
- 需要人参与的地方, 应该在 harness 层面暂停整个循环, 用结构化的问题问人 (权限策略的 `ask`, V5 的 escalate), 而不是把子进程的输入交给人: 那样无法用于无人值守的批量评测, 输入的内容不会被记录, 也绕过了权限检查.

**代价**
按名字过滤是黑名单, 名字不含这些词的敏感变量仍然会被继承.

## ADR-006 超时两阶段终止整棵进程树

**背景**
命令可能卡住, 也可能启动子进程 (shell → python → pytest → 测试启动的进程). 只终止最外层的 shell, 它启动的进程会继续在后台运行.

**决定**

- 每条命令在独立的进程组里启动 (Windows 用 `CREATE_NEW_PROCESS_GROUP`, POSIX 用 `start_new_session`);
- 超时后分两个阶段: 先发送中断信号 (Windows 发 `CTRL_BREAK_EVENT`, POSIX 发 `SIGINT`), 给 5 秒的宽限期, 让程序有机会清理; 到期还没退出, 再强制终止整棵进程树 (`taskkill /T /F` 或 `killpg SIGKILL`);
- 等待命令时被 Ctrl+C 打断, 直接强制终止整棵进程树, 不给宽限期, 然后继续抛出异常.

**理由**

- 直接强制终止, 程序来不及清理 (比如 pytest 的临时文件, 写了一半的缓存);
- 独立的进程组, 才能一次终止所有子进程, 不留下孤儿进程;
- 独立的进程组收不到终端上的 Ctrl+C, 所以人按下 Ctrl+C 时, 必须由我们主动终止它们. 人按 Ctrl+C 是想立刻停下, 所以不走宽限期.

**代价**
中断信号是"尽力而为": 在 Windows 上, 正在阻塞的调用 (比如一次很长的 `time.sleep`) 不会被打断, 程序要等调用返回后才能处理信号, 可能来不及在宽限期内退出. 测试 `test_exec_timeout_lets_process_clean_up` 记录了这一点.

## ADR-007 文件原子写入

**背景**
写文件的过程中, 进程可能被终止 (超时, Ctrl+C, 崩溃). 直接覆盖写入的话, 目标文件可能只剩下一半的内容.

**决定**
先把完整的内容写进同一目录下的临时文件, 复制原文件的权限, 再用 `os.replace` 一次性替换目标文件. 任何一步失败都删除临时文件.

**理由**

- 在同一个磁盘上, `os.replace` 只是一次重命名, 要么完全成功, 要么完全没有发生;
- 临时文件必须和目标文件在同一个目录: 跨磁盘的"重命名"实际上是复制, 就不是原子的了;
- 源代码被写坏一半, 是最难排查的一类问题: 测试会以奇怪的方式失败, 模型会去修一个本来不存在的问题.

**代价**
每次写入多一次文件操作, 对这个场景可以忽略.

## ADR-008 按 ACI 原则设计工具

**背景**
ACI (agent-computer interface) 指的是: 工具是给模型用的界面, 和给人用的界面一样需要认真设计. 工具的说明, 参数, 报错信息, 直接决定模型能不能用对它.

**决定**
V1 提供 4 个工具: `read_file`, `edit_file`, `write_file`, `run_command`. 具体的规则:

- **不接受未定义的参数** (`extra="forbid"`): pydantic 默认会悄悄丢掉多余的参数. 模型把 `start_line` 写成 `strat_line` 时, 参数被丢掉, 退回默认值, 模型却以为设置成功了, 很容易陷入反复重试;
- **报错要告诉模型下一步怎么做**: 例如"文件不存在, 可以用 run_command 工具执行 git ls-files 查看仓库里有哪些文件";
- **edit_file 要求 old_str 在文件中只出现一次**: 出现多次时拒绝, 让模型多带几行上下文, 而不是猜它想改哪一处;
- **保留文件原来的换行符** (CRLF 或 LF): 不保留的话, 改一行会让整个文件在 diff 里都变成"已修改";
- **修改后显示修改处前后 3 行**: 只看改动本身, 没法判断缩进对不对, 位置对不对;
- **输出过长时保留开头 1/4 和结尾 3/4**: 以 pytest 为例, 结尾的汇总对模型最重要;
- **工具说明, 报错, prompt 中提到的工具名都必须存在**: 由测试检查, 防止工具改名后, 模型照着旧名字去调用.

**理由**
这些规则都来自具体的失败场景: 模型在参数拼错时死循环, 在找不到文件时反复猜路径, 在 CRLF 文件里改出整个文件的 diff.

**代价**
`run_command` 能做任何事, 它让文件工具的很多限制失去了意义 (见[已知的局限](#已知的局限)). 现在保留它, 是因为测试, 安装依赖, 搜索代码都离不开它.

## ADR-009 权限策略: 判断与执行分离, 黑名单只是第一道防线

**背景**
模型可能做出危险或者违背任务要求的操作: 修改测试让测试通过, 把目标依赖降级回旧版本, 读取密钥文件, `git push`, 递归删除目录.

**决定**

- **判断与执行分离**: `policy.py` 只负责判断 (决策点, PDP), 返回 allow, deny, ask 三种结果; `loop.py` 负责执行判断 (执行点, PEP), 被拒绝的调用不交给工具注册表执行. 所有工具调用都必须经过这一个入口;
- **V1 的 ask 按拒绝处理**: 还没有确认界面, 拿不准时选择更安全的一边 (fail-closed);
- **每条规则都对应一个具体的失败场景**, 说不出场景的规则不加;
- **匹配之前先规范化**: 路径统一斜杠, 处理 `.` 和 `..`, 统一大小写 (Windows 上 `Tests` 和 `tests` 是同一个目录); 命令按 `&&`, `||`, `;`, `|`, `&`, 换行拆成子命令, 逐条检查;
- **规则同时放进 system prompt** (`describe()`), 让模型一开始就知道哪些事不能做;
- **拒绝原因里写清楚应该怎么做**, 避免模型换一种写法反复尝试.

**理由**

- 分离之后, 策略可以单独测试: 给它一个工具调用, 检查判断结果, 不需要运行 agent;
- 以后换一种策略 (比如从题目配置读取规则), loop 不用改;
- 文件路径用"目录名"和"文件名通配符"分开匹配, 是为了避免 `fnmatch` 的 `*` 跨过 `/` 造成误判; 命令拆成子命令, 是为了避免规则跨过 `&&` 误伤后面的正常命令.

**代价**
这是一份黑名单, 只能拦住**无意的**常见错误, 拦不住**有意的**绕过: 例如 `python -c "open('tests/test_x.py', 'w')"` 就能绕过"不能修改测试文件". 测试 `test_known_bypass_is_not_caught` 专门记录了这一点. 因此它必须和另外两道防线一起使用:

- **V4 的独立验证**: 不管用什么方法, 事后都检查测试有没有被改, 依赖的版本对不对, 不相信 agent 的任何说法;
- **V9 的沙箱**: 在容器里运行, 即使绕过了规则, 影响也被限制在容器以内.

规则在代码里强制执行, 在 prompt 里告知模型; 安全只能依靠前者.

## ADR-010 prompt 模板化, 版本化, 可复现

**背景**
prompt 会频繁调整. 调整之后需要回答: 这次运行用的是哪一版 prompt? 效果变好是因为 prompt 改了, 还是因为别的?

**决定**

- prompt 写在 `prompts/` 目录下的 Markdown 文件里, 文件名带版本号 (`system_v1.md`, `task_v1.md`). 修改时新建 `v2`, 不改动已有的版本;
- 用标准库的 `string.Template` 填入变量. 缺少变量, 多出变量, 不合法的占位符都直接报错;
- 每次渲染都记录模板的哈希和渲染结果的哈希;
- system prompt 只放稳定的内容 (角色, 原则, 环境, 规则), 每个任务不同的内容放在第一条 user 消息里.

**理由**

- 少传一个变量, 模型就会看到一个原样的 `$target`, 而且不会有任何报错. 必须在启动时就发现;
- 多传变量, 通常说明模板里的占位符写错了名字, 这个值根本没有进入 prompt;
- 有了哈希, V2 的 trace 可以准确记录每次运行用了哪一版 prompt; V6 评测时可以让两个版本跑同一批题, 用数据比较;
- system prompt 保持稳定, 可以利用服务商的前缀缓存, 降低成本和延迟.

**代价**
不用模板引擎 (比如 Jinja), 模板里没有条件和循环. 列表这类内容需要在代码里先整理好再填入 (例如 `bullet_list`).

## ADR-011 agent 循环: 失败也是一种结果

**背景**
一次运行可能以很多种方式停下来: 模型说完成了, 模型说需要人处理, 次数用完, 回复被截断, 调用模型失败, 人按了 Ctrl+C.

**决定**

- 每一种停止方式对应一个 `Status`, `run()` 总是返回 `RunResult`, 不把模型调用的异常抛出去;
- 模型说完成了, 记为 `finished` 而不是 `success`: 这只是模型自己的说法, 是否真的完成由 V4 的验证判断;
- 判断有没有工具调用, 看回复里有没有 tool_use 块, 而不是只看 `stop_reason`: 有些兼容接口的 `stop_reason` 不可靠;
- 同一条回复里的所有工具结果放进同一条消息, 和 tool_use 一一对应; 工具被拒绝或者执行失败, 也要回复一个 `is_error=True` 的结果;
- 回复因为超出长度上限被截断时, 其中的工具调用一律不执行 (参数可能只写了一半); 连续 3 次截断就停止;
- 正常结束的停止原因用白名单 (`end_turn`, `stop_sequence`), 不认识的原因按错误处理;
- 循环在关键时刻调用一个事件回调 (`on_event`), 自己不打印, 也不写文件.

**理由**

- 批量评测时, 一道题失败只记一条结果, 不能让整个评测中断;
- `finished` 和 `success` 分开, 是区分"自己说的"和"验证过的";
- 半截的 `write_file` 会把文件覆盖成只剩一半的内容;
- 事件回调是观察者模式里最简单的形式 (一个钩子函数). 终端打印和 V2 的 trace 都通过它实现, loop 不需要为此修改. 需要多个订阅者时, 在调用方把多个处理函数组合成一个.

**代价**
事件回调是同步的: 处理函数慢, 循环也跟着慢; 处理函数抛出的异常会中断运行. 这是有意的: trace 写失败了, 应该让人马上看到.

## ADR-012 上下文压缩推迟到有 trace 数据之后

**背景**
每轮的工具输出都留在对话历史里, 历史会越来越长. 常见的做法有: 清除旧的工具结果, 生成摘要, 把笔记写到外部文件, 把子任务交给独立的上下文.

**决定**
V1 只做静态的上下文工程: 稳定的 system prompt, 输出截断, 精简的工具说明. 动态的压缩推迟到 V2 有了 trace 数据之后再做.

**理由**

- 不知道 token 实际花在哪里, 就不知道该压缩什么;
- 压缩一定是有损的. 必须先确定哪些内容的"源头"还在, 可以安全地丢掉 (文件内容可以用 read_file 重新读取), 哪些内容一旦丢掉就找不回来 (任务说明, 被拒绝过的操作, 已经试过并且失败的思路);
- V2 的 trace 会完整保存原始记录, 压缩上下文不会丢失排查问题需要的信息.

**代价**
在 V2 之前, 很长的任务可能超出上下文窗口, 这时调用模型会失败, 结果记为 `llm_error`. `max_turns` (默认 40) 限制了历史的最大长度.

## ADR-013 trace: 用文件记录, 通过互相隔离的事件回调写入

**背景**
V1 的两次运行 ([docs/v1/runs/](v1/runs/)) 只能看到终端上每段内容的前 200 个字符: 看得到 agent 做了什么, 看不到它为什么这样做 (thinking 块完全看不到), 也无法统计每轮的上下文长度和耗时. 运行 002 中, agent 在测试通过之后做了一个全局性的修改, 引入了所有测试都发现不了的缺陷, 它的理由只能靠猜.

**决定**
每次运行在 `runs/<运行编号>/` 下生成一个目录:

| 文件 | 内容 |
|---|---|
| `meta.json` | 任务, 配置 (白名单, 不含密钥), 运行环境, harness 自己的 commit, 目标仓库开始和结束时的 HEAD, 两个 prompt 的哈希, 权限规则, 结果 |
| `events.jsonl` | 每行一个事件, 带序号, 墙上时间和单调时间. 内容完整: 包括模型回复中的 thinking 块, 以及每次调用模型, 执行工具的耗时 |
| `messages.json` | 结束时完整的对话历史 |
| `prompts/` | 渲染好的 system prompt 和任务消息 |
| `diff.patch` | 和开始时的 HEAD 相比的全部改动, 包括新建的文件 |

写入的方式:

- **trace 就是一个事件回调**: `TraceWriter` 实现了 `__call__(event, data)`, 和终端打印一起用 `fan_out` 组合后交给 loop. loop 不知道 trace 的存在, 为了 trace, loop 的流程没有任何改变, 只是在事件里补充了完整的回复内容和耗时;
- **订阅者之间互相隔离** (`fan_out`):
  - 数据隔离: 每个订阅者拿到事件的一份深拷贝. 事件里的 `content` 和对话历史是同一个对象, 订阅者改了它, 下一次请求就会带着被改过的 thinking 块发出去, 签名对不上, 接口会拒绝;
  - 执行隔离: 一个订阅者出错, 其他订阅者照样收到事件, 全部执行完之后, 再把第一个错误抛出去. `KeyboardInterrupt` 不在此列, 立刻生效;
  - 出错之后怎么办, 由组装的人决定: trace 是关键的订阅者, 出错会让运行停下; 终端打印用 `best_effort` 包装, 出错只提示一次, 不影响运行. trace 排在前面;
- **事件逐行追加, 每写一行就 flush**: 程序崩溃或被 Ctrl+C 打断时, 已经发生的事件都还在. 读取时, 最后一行不完整就忽略 (写到一半时被强制终止), 中间的行损坏则报错;
- **`meta.json` 原子写入**: 开始时写一次 (`running`), 结束时先写 messages 和 diff, 最后才更新状态. 状态是"这份记录是否完整"的标志, 必须最后写. harness 自己出错时记为 `crashed` 并附上调用栈;
- **写入磁盘之前脱敏**: 把密钥的值替换成 `***`, 先替换长的. 少于 8 个字符的值不处理, 以免误伤正常的内容;
- **运行编号 = 时间 + 仓库名 + 4 位随机字符**: 按名字排序就是按时间排序; 目录已经存在时直接报错, 绝不覆盖已有的记录;
- **`python -m bumpwise show <目录>`**: 按轮次显示 thinking, 回复, 工具调用和结果, 最后统计上下文的增长, 耗时和工具的使用次数. 它只依赖 trace 的文件格式, 不依赖运行时的类; 缺少的字段当作 0, 不认识的事件直接跳过.

**理由**

- **用文件, 不用数据库, 也不用 LangSmith 这类服务**: 一次运行只有几 MB, JSONL 可以用任何工具读取 (grep, jq, pandas), 不需要额外的服务, 也不会把仓库的代码发给第三方. V6 需要汇总很多次运行时, 再把它们导入数据库;
- **记录事件, 而不是每轮完整的请求**: 每轮的请求都包含全部历史, 全部记下来, 体积会随轮数平方增长. 事件只记录每轮新增的内容, 完整的对话历史可以从事件还原, 结束时另外保存一份;
- **结果由四样东西共同决定 (模型, prompt, harness, 目标仓库), 四样都要记下来**: 运行 002 和 001 之间, prompt 和 harness 同时变了. 没有 harness 的 commit, 就分不清是哪一个改动起了作用;
- **配置用白名单逐个列出**: 用 `asdict` 一次导出的话, 以后 Settings 新增的敏感字段会自动进入 trace. 脱敏只认识已知的密钥值, 能不写进去的, 就从源头上不写;
- **diff 和开始时的 HEAD 比较, 包括未跟踪的新文件**: 即使 agent 绕过规则提交了代码, 或者新建了文件, 改动也不会漏掉. git 的 status, ls-files, diff 都会把中文文件名转义成八进制, 所以三条命令都加上 `core.quotePath=false`;
- **不同的停止方式区分开**: agent 没有完成任务 (`max_turns` 等) 是正常的结果; harness 自己出错 (`crashed`) 说明评测本身有问题, V6 统计时这道题要重跑.

**代价**

- 事件回调是同步的: 订阅者慢, 循环也跟着慢. 现在的两个订阅者都很快 (追加一行文件, 打印一行). 以后如果有慢的订阅者 (比如把事件上报到远程的监控服务), 再改成异步: 每个订阅者有自己的队列和线程. 现在不做, 是因为异步会带来新的问题: 程序退出或 Ctrl+C 时, 队列里还没写完的事件怎么办;
- 每个订阅者都深拷贝一次事件, 多占一些内存和时间. 事件最大也就几万个字符, 可以忽略;
- 脱敏只处理已知的密钥值. 仓库里的其他凭据仍然可能出现在工具的输出中. `runs/` 已经加入 `.gitignore`, 不会被提交;
- 运行记录不会自动清理, 需要时手工删除.

## ADR-014 按层分包, 依赖只能从上往下

**背景**
V2 和 V3 开始时, 新文件都是临时决定放在哪里的: `trace_view.py`, `task.py`, `workspace.py` 都放在了 `bumpwise/` 的根目录, `__main__.py` 长到了 376 行, 里面混着命令行参数, 终端打印, 运行和 trace 的组装, show 命令. 单看每个决定都说得通, 合在一起, 从目录上已经看不出哪些文件属于同一层, 谁依赖谁. 后面还有准备流水线 (V3), grader (V4), 批量评测 (V6).

**决定**

```
bumpwise/
├── config.py        配置
├── llm/             模型接入
├── env/             执行平面: Environment 接口和实现
├── tools/           agent 的工具 (通过 env 操作)
├── harness/         agent 运行时: loop, policy, prompts, trace
├── task/            题目, 工作区, 准备流水线 (V3). 不知道模型的存在
├── runner/          编排一次运行: (准备) → agent 循环 → 运行记录 (V3 模块 4 新增). 不知道命令行的存在
├── cli/             命令行: 每个子命令一个模块 (run.py, show.py), 加上终端打印 (progress.py)
└── __main__.py      只有几行, 调用 cli.main
```

以后的 `grading/` (V4) 放在 `runner/` 和 `task/` 之间 (runner 在 agent 结束后调用它), `evaluation/` (V6) 放在 `cli/` 和 `runner/` 之间 (它批量调用 runner).

依赖只能从上往下, 下层不知道上层的存在:

```
cli  →  runner  →  task  →  harness  →  tools  →  env
                             ↓
                            llm  →  config
```

V3 模块 4 新增 `runner/` 的原因: "加载题目 → 创建工作区 → 准备 → agent 循环 → trace"这段编排, 原来一半在 `cli/run.py` 里. 以后 V6 的批量评测也要用它, 而批量评测不经过命令行; 放进 `task/` 的话, `task` 就要依赖 `llm` 和 `tools`, 而题目, 工作区, 准备流水线本来和"用哪个模型"无关.

- 每个包允许依赖谁, 写在 `tests/test_architecture.py` 的 `ALLOWED` 里. 测试扫描每个文件的 import, 违反依赖方向就失败;
- 新增一个包时, 不先在 `ALLOWED` 里声明它在哪一层, 测试也会失败;
- 子命令的模块各自提供 `add_parser` 和 `execute`, `cli/__init__.py` 只负责组合. 新增子命令只需要新增一个模块;
- 测试文件按层命名: `test_<包>_<模块>.py` (例如 `test_harness_loop.py`, `test_cli_run.py`), 和代码的结构对应;
- 每次新建文件时, 先想清楚它属于哪一层; 每开始一个新的模块 (或版本), 都回头检查一次目录结构.

**理由**

- **依赖方向决定了能不能复用**: V6 的批量评测要在没有命令行的情况下运行题目, 所以 `task` 不能依赖 `cli`; 换成 Docker 时, 只需要替换 `env` 的实现, 所以 `env` 不能依赖任何上层;
- **用测试守住规则, 而不是靠记忆**: 规则只写在文档里, 迟早会有人 (包括我们自己) 为了方便, 在下层导入一个上层的东西. 测试会在那一刻失败;
- **"新包必须先声明"是在逼自己思考结构**: 新建一个包, 必须先回答"它在哪一层, 可以依赖谁", 这正是每到一个新模块时要做的思考.

**代价**

- 移动文件之后, 已有的导入要跟着改. 这次用 `task/__init__.py` 重新导出, 让 `from bumpwise.task import load_task` 的写法不变;
- 架构测试只检查包和包之间的依赖, 不检查包内部的结构. 包内部的整理, 仍然靠每次新建文件时的思考.
- 项目根目录下的 `tasks/` (题目文件, 数据) 和 `bumpwise/task/` (代码) 名字相近, 但位置和用途都不同, 可以接受.

## ADR-015 题目是声明式的数据, 准备工作由流水线在全新的工作区里完成

**背景**
运行 001-003 之前, 准备工作都是手工完成的: 建 worktree, 修改 `pyproject.toml` 并单独提交, 建 venv, 安装指定的版本, 跑测试确认失败, 把失败的情况手工写进 `--state`, 每次重跑之前 `reset --hard`. 这些都是 V0 `procedure.md` 中"代码"的步骤, 靠人来做会出错, 别人无法复现, 也没法批量 (V6 要在很多题上各跑很多次).

**决定**

1. **题目是声明式的数据** (`tasks/<id>.toml`, 格式定义在 `task/spec.py`):
   - 写明仓库, 起点提交 (完整的 40 位哈希), Python 版本, 安装命令, 测试命令, 要迁移的依赖;
   - 版本分两种: `target` 是范围 (写进依赖声明, 告诉 agent 的目标), `from_version` / `to_version` 是精确的版本 (实际安装的, 保证每次的环境一样);
   - 依赖声明的修改 (`edits`) 用精确替换, 原文必须恰好出现一次, 而不是解析各种依赖文件的格式;
   - 严格校验: 禁止未定义的字段, 加载后不可修改, id 必须和文件名一致. 测试会检查题库里的每一道题;
   - `description` 只给人看, 不写分析的结论: 一旦被拼进 prompt, 就等于泄题.
2. **工作区** (`task/workspace.py`): 创建工作区相当于"开一个沙箱", 由控制平面完成; 之后的一切都通过返回的 `Environment` 进行.
   - `WorkspaceProvider` 接口, 现在只有本地实现, 以后加 Docker 的实现;
   - 远程仓库在本地有一个只增不改的镜像, 只有第一次需要联网; 起点提交不在任何分支上时单独 fetch;
   - 每次运行从镜像克隆一份全新的仓库 (而不是 reset 或 git worktree): 干净, 可以并行, 运行结束后保留, 方便事后检查. worktree 和主仓库共用 stash 和分支名, 多次运行之间会互相影响;
   - 镜像先克隆到临时目录, 完成后再一次性改名; 检出之后再确认一次 HEAD;
   - **工作区里只有起点提交和它之前的历史**: 新建一个空仓库, 只从镜像 fetch 起点提交, 不添加 origin. V4 开始时发现,
     原来整个克隆镜像的做法会把起点之后的提交也带进工作区: cortex 的 master 分支已经合并了迁移, 参考答案的提交 (隐藏测试的来源) 也在,
     agent 执行一次 `git diff master` 就能拿到答案. 检查 002-004 的记录, agent 从来没有用过 git log / show / checkout, 结果仍然有效, 但这只是运气.
     为了能按提交 fetch, 镜像设置了 `uploadpack.allowReachableSHA1InWant`, 并把每个起点提交钉在 `refs/bumpwise/pins/` 下.
3. **准备流水线** (`task/prepare.py`): 检查 Python → 建 venv 并确认它生效 → 安装 → 装上旧版本并确认版本 → 基线测试 → 修改依赖声明并提交 → 装上新版本并确认版本 → 升级后的测试 → 冻结.
   - 每一步都"做完再验证", 每一步都作为 `prepare` 事件写进 trace;
   - 基线必须通过 (评测时), 否则题目无效. 业务里可以只记录 (`require_passing_baseline=False`);
   - harness 修改依赖声明的提交就是 agent 的起点: agent 的改动都和它比较, harness 的改动不会被算成 agent 的;
   - 冻结: 准备过程中产生的未跟踪文件加入 git 的 exclude (向 git 查询 exclude 文件的位置), 已跟踪的文件被修改了就报错, 最后确认工作区是干净的;
   - 给 agent 的"当前状态"由升级后的真实测试结果生成, 只写事实;
   - 准备失败抛出带着步骤名的 `PrepareError`.
4. **runner** (`runner/`, 见 ADR-014): 把"题目 → 工作区 → 准备 → agent 循环 → trace"串成一次完整的运行.
   - `run_task` (照着题目) 和 `run_repo` (在已有的仓库上, 调试用) 共用同一段运行 agent 并记录的代码;
   - 模型客户端和终端打印都由调用方传进来 (依赖注入, 事件回调), runner 不打印, 不决定退出码;
   - 运行的结果分四类, 都写进 meta: agent 的停止方式 (算进 agent 的成绩), `prepare_failed` (题目或环境的问题), `crashed` (harness 的 bug), `interrupted` (循环之外被 Ctrl+C 打断). 命令行上, 准备失败的退出码是 20;
   - 谁创建工作区, 谁负责关闭; 结束时的 HEAD 和改动放进返回值, 因为以后的工作区 (容器) 在运行结束后就销毁了.

**理由**

- 题目是数据, 新增一道题只需要加一个文件; 题目可以审查, 比较, 版本化. 业务里用户只需要发送"仓库, 依赖, 目标", 其余的字段由仓库的配置文件, 锁文件和最新的提交补全, 但最后得到的是同一个 `TaskSpec`, 后面的代码不用改;
- 精确的版本和全新的工作区, 让同一道题的每次运行都从同样的起点开始. 运行 004 中, 流水线准备出来的起点和 003 之前手工准备的完全一致;
- "做完再验证"把环境的问题挡在 agent 开始之前: 在错误的环境里白跑 40 轮, 花钱, 还会得出错误的结论;
- 准备失败和 agent 失败分开, 评测的分数才不会失真. 运行 004a 第一次尝试时, 克隆镜像失败, 结果记为 `prepare_failed`, 没有调用模型, 也没有花钱.

**代价**

- 每次运行都重新建 venv 和安装依赖 (cortex 约 33 秒). 以后可以缓存: 同一道题, 同一份依赖, 环境只构建一次 (分层镜像);
- 每次运行保留一份带 venv 的工作区, 会越来越占空间, 需要清理的办法;
- 测试输出的摘要只适配 pytest; 依赖声明只能精确替换, 不会自动修改;
- 工作区必须是普通的克隆, 不支持 git worktree;
- 网络依赖本机的代理设置: 运行 004a 时, git 的全局配置中的代理不可用, 需要临时改用别的代理.

## ADR-016 在评测之后新增"经验与记忆" (V7)

**背景**
项目的目标是 Agentic Growth Infra, 其中的 "Growth" 指 agent 能从做过的任务里积累经验, 越做越好, 而不是每次都从零开始.
我们其实已经手工完成过一次学习循环: 运行 001 → 总结出 6 个问题 → 写 system_v2 → 运行 002 (6 项中 5 项生效). 但每一步都靠人.
另一个例子: "带别名的字段用字段名赋值" 这个行为变化, 002, 003, 004 三次都漏掉了. 如果 agent 能记住上次的教训, 第四次就不会再漏.

**决定**
在 V6 (评测) 之后新增 V7 "经验与记忆", 原来的 V7 (统一接口) 和 V8 (沙箱) 顺延为 V8 和 V9. 代码注释和本文档中的编号已经同步更新, 之前的运行记录保留当时的写法.

V7 的大致设计 (到时候再细化):

- **记忆的种类**: 情节记忆 (过去的运行, 已经有了: trace), 语义记忆 (提炼出的知识, 比如某个依赖的某种行为变化), 程序记忆 (prompt, 工作流程, 工具, 现在只能靠人改);
- **学习的循环**: 运行 (trace) → 评分 (grader) → 提炼经验 (模型或人) → 审核 → 写进记忆 → 下次运行时按依赖和版本取出, 放进 prompt;
- **每条经验都带上**: 适用的范围 (依赖, 版本), 证据 (来自哪次运行, 哪一项检查), 状态 (待审核, 已验证, 已废弃);
- **一开始用精确的键查找** (依赖名 + 版本), 不做向量检索, 符合"暂时不做 RAG"的约定;
- **记忆也要版本化**: 每次运行在 trace 中记下用的是哪个版本的记忆, 和 prompt 的哈希是同一个道理.

**理由**

- **为什么排在评测之后**: 记忆依赖 grader 判断经验的好坏, 依赖评测证明记忆真的有用. 记忆可能有害:
  - 学到错误的经验 (比如把 002 中"给所有模型加 `coerce_numbers_to_str`"当成好的做法, 而它恰恰引入了缺陷);
  - 过度概括 (在一个仓库上学到的规则, 在别的仓库上不成立);
  - **污染评测**: 如果记忆来自隐藏测试的结果, 下次在同一道题上运行, 就等于提前知道了答案. 所以必须像机器学习那样把"训练"和"测试"分开: 从一部分题目上学到的记忆, 只能在另一部分题目上评测效果, 而且要做"有记忆 / 没有记忆"的对比 (消融实验);
- **为什么排在统一接口之前**: Growth 是项目的核心目标. 先证明 agent 能越做越好, 再考虑怎样提供给别人使用.

**现在就为它做的准备** (不增加额外的工作量):

- V4 的评分报告做成结构化的: 每一项检查都有明确的结果和原因, 以后可以直接拿来提炼经验;
- 题目里已经有依赖和版本, 以后可以直接作为查找记忆的键;
- trace 里已经记录了 prompt 的哈希, 以后再加一项"记忆的版本".

**代价**
沙箱 (V9) 又往后推了一个版本. 在此之前, 本地环境只能用于可信的仓库, 已知的漏洞 (ADR-009, 以及 agent 可以读本机上的镜像目录) 会存在得更久.

## ADR-017 grader: 只看结果, 不相信 agent 的说法

**背景**
运行 001-004 结束后, 每次都按 V0 的验证清单手工检查一遍: 原有测试, 警告的来源, 静态扫描, 新旧对比, 隐藏测试, 枚举成员, 改动范围.
每次都是同样的几条命令, 费时间, 也容易漏. 而且 agent 自己的说法不能作为依据: 三次运行都在 40 轮用完时停下, 没有最终回复;
就算有, "测试全部通过"也不等于迁移正确. 002 的 210 个测试全部通过, 却给 4 个枚举加了一个多余的成员.
V6 要在很多题上各跑很多次, V7 要根据评分提炼经验, 都需要一个自动, 可复现, 结构化的评分.

**决定**

1. **只看结果**: grader 不读 agent 的最终回复和对话历史, 只看三样东西: 工作区里的改动, 题目里的评测信息, trace 里 agent 调用过的工具 (只用于隔离检查).
2. **评测信息写在题目里, agent 看不到**: 题目文件的 `[evaluation]` 段 (源代码目录, 要比较的包, 禁止的写法, 隐藏测试). 流水线和 prompt 都不读它; `tasks/` 目录也在隔离检查的范围里.
3. **8 项检查**, 每一项都对应一次运行中真实出现过的问题, 或者人工检查中的一步:

   | 检查 | 看什么 | 来源 |
   |---|---|---|
   | visible_tests | 原有的测试是否全部通过 | 验证清单 |
   | source_warnings | 源代码是否还产生废弃警告 (测试文件自己的警告不算) | 验证清单 |
   | forbidden_patterns | 源代码中是否还有旧写法 (`parse_obj(`, `class Config:` 等) | 验证清单 |
   | hidden_tests | 参考答案里的测试 (agent 看不到) 是否通过, 已知的失败要写明原因 | 002-004 都漏掉了带别名字段的赋值 |
   | api_surface | 新旧版本的公共接口: 模块里有哪些类, 枚举有哪些成员, 模型有哪些字段 | 002 的枚举缺陷, 所有测试都没有发现 |
   | dependency | 装的是不是目标版本, 依赖声明有没有被改回去 | 权限策略的规则, 不相信策略, 再查一次 |
   | change_scope | 有没有改测试, 依赖文件, CI 配置, 有没有产生提交, 改动是否都在源代码目录里 | 同上 |
   | isolation | agent 的命令和路径里有没有出现镜像, 题目文件, 运行记录的路径 | V4 开始时发现的答案泄露 |

4. **结果是结构化的**: 每一项返回 `CheckResult` (名字, 状态, 一句话的结论, 细节, 数据). 状态有 4 种:
   - `pass` / `fail`: 只要有一项 fail, 总评就是 fail;
   - `warn`: 需要人看一下, 不影响总评. 正确的迁移也可能改变接口 (`__root__` 改成 `RootModel`), 不能一律判错;
   - `skip`: 缺少输入 (没有隐藏测试, 没有 trace), 明确写出来, 而不是当作通过.
5. **检查在目标仓库自己的环境里运行**: 用 pytest 插件拿到每个测试的结果和警告的来源 (而不是解析文字输出); 收集出错时不中止整个运行; 检查用的脚本放进工作区里一个随机命名, 自带 `.gitignore` 的目录, 不会被算成改动.
6. **隐藏测试只在控制平面读取**: 从本机的镜像里 `git archive` 出参考答案提交里的测试文件 (`files_at`), 不经过工作区, 工作区里也没有那个提交. 运行时用自己的 pytest 配置 (`rootdir`, `confcutdir`), 不受仓库的配置和 conftest 影响. 读取时关掉换行符转换, 同一个提交在任何机器上读出来都一样.
7. **接口表面的基准是"旧代码 + 旧版本"**: 评分时新建一个工作区, 只跑准备流水线的前半段 (到基线测试为止), 记下它的接口表面, 再和 agent 改完之后的对比. 分三级: 枚举成员的增减和值的变化, 公开的名字不见了, 模块无法导入, 判为 error (使用者的代码几乎一定会坏);
   模型少了字段, 基类或函数参数变了, 判为 warning (可能是合理的迁移); 新增的名字和字段只记录 (info).
8. **接进 runner** (`runner/grade.py`):
   - agent 正常结束 (`finished`) 后自动评分; 其他停止方式下, 工作区停在做到一半的状态, 不自动评分;
   - 评分出错或被 Ctrl+C 打断只记录下来, 不影响运行本身的状态: agent 的结果和评分是两件事;
   - 结果写进 `grade.json` (完整的报告) 和 `meta.json` 的 `grade` 字段 (状态, 总评, 评分时 harness 的版本). `grade.json` 存在, 当且仅当评分完成;
   - 评分读的是磁盘上的 `events.jsonl`, 评分自己的事件不写进去: 自动评分和事后补评分得到同样的输入;
   - `grade` 命令可以给已有的运行补评分或者重新评分. 评分之前, 用 trace 里的 `diff.patch` 核对工作区, 运行结束后被改过就拒绝 (除非 `--allow-modified`).

**理由**

- **不相信 agent, 也不完全相信自己的权限策略**: 策略是黑名单 (ADR-009), 拦不住所有的绕过; grader 从结果出发再查一遍, 两道防线互相独立;
- **离线评测**: agent 只运行一次 (要花钱), 评分可以反复进行. grader 改进以后, 用 `grade` 命令把旧的运行重新评一遍, 就能看出新的检查发现了什么. 这次给 002-004 评分就是这样做的, 三次运行的人工结论全部复现 ([grade-002-004](v4/runs/grade-002-004.md));
- **结构化的结果** 可以直接统计 (V6), 也可以直接用来提炼经验 (V7, ADR-016);
- **接口表面对比** 补上了测试的盲区: 测试只检查"用到的行为", 多出来的枚举成员不影响任何一个测试, 但会影响遍历枚举的使用者.

**代价: 奖励欺骗 (reward hacking)**

grader 就是 agent 的目标. 现在是人在看结果, 以后 V6 用它比较不同的 prompt, V7 用它决定哪些经验是好的, 优化的压力会越来越大.
任何"能被满足, 但不等于迁移正确"的检查, 都可能被钻空子. 现在知道的漏洞:

- **评分在 agent 用过的环境里进行**: venv 被 git 排除了, 改动范围看不到它. agent 可以修改 site-packages 里的 pydantic, 或者加一个 `.pth` 文件, 让测试通过; 依赖检查只看版本号. 被 `.gitignore` 忽略的文件也一样看不到;
- **检查和被检查的代码运行在同一个环境里**: 被测代码在导入时可以篡改 pytest 插件写出的结果. 评分的可信程度, 不会超过执行平面的可信程度;
- **隔离检查是字符串匹配**: 相对路径 (`..\..\_mirrors`), 环境变量, 在脚本里拼出来的路径都查不到. 本地环境下真正的隔离只能靠 V9;
- **禁止写法是字符串匹配**: 可以绕过 (拼接字符串), 也可能误报 (所以没有加 `.json(`);
- **隐藏测试只有一份参考答案** (作者的 PR): 和作者不同但同样合理的做法会被判失败, 已知的失败要靠人维护;
- **评分的细节会泄露隐藏测试**: `grade.json` 里有隐藏测试的名字和失败的原因. V7 提炼经验时, 不能把同一道题的评分细节写进记忆, 否则下次在这道题上评测, 就等于提前知道了答案 (ADR-016 中"训练和测试分开").

前两条的根本解决办法是: **不在 agent 的工作区里评分**, 而是把 `diff.patch` 应用到一个由流水线全新准备的工作区上, 在那里评分.
这样 venv 里的改动, 被忽略的文件都不会被带过来, 只有被 git 跟踪的改动才算数. 这和"在沙箱里改完, 怎样迁移到真实的仓库"是同一个问题: 能离开沙箱的只有 diff.
计划在 V9 (沙箱) 时一起做, 那时工作区在运行结束后就会销毁, 评分本来也只能这样做.

**其他代价**

- 每次评分都要准备一次旧版本的环境 (cortex 约 25 秒, 28 MB), 而它只取决于题目, 和是哪次运行无关. 以后按题目缓存;
- 总评只有 pass / fail. 002 (2 项失败) 和 003 (1 项失败) 看不出差别, V6 比较时需要更细的分数;
- 只给 `finished` 的运行自动评分. 002-004 都是 `max_turns`, 是手动评的;
- grader 只适配 Python 和 pytest.

## ADR-018 参数和设计都要有数据依据, 不凭空设定

**背景**
V5 设计预算时发现, 一直在用的"最多 40 轮"没有任何依据: 运行 001 设的是 15 轮, 测试一次都没跑通, 002 就改成了 40, 之后一直沿用.
回头看, 这个数字有三个问题: 轮数不是成本的单位 (004 第 40 轮的输入是第 1 轮的 24 倍, 最后 10 轮占了总量的 37%);
不同的题目需要的轮数不一样; agent 根本不知道有这个限制 (prompt 里一个字都没提).
项目里还有很多这样的数字, 以及"应该加一个某某检查"这样的设计, 一开始都是凭直觉定的.

更重要的是, 好几次凭直觉得出的判断, 被数据推翻了:

| 凭直觉的判断 | 数据显示 | 结果 |
|---|---|---|
| cmd.exe 里没有 `tail`, 所以 `\| tail` 会失败 | 这台机器上有 tail (Git for Windows 自带). 真正的问题是管道的退出码来自最后一个命令: 004 第 1 轮 pytest 失败 (退出码 4), 显示的却是 0 | 护栏改成检查"退出码被管道掩盖", 而不是"用了 tail" |
| "先通读所有文件"是迷路了, 需要护栏 | 003 的 trace 显示这是有意的策略 (先摸清全部用法, 再整体迁移) | 不加这个护栏 |
| 按"用到这个依赖的文件数"估算预算 | 只有 1 道题, 3 次运行, 拟合不出系数 | 收回. 用一个明确写出来的默认值, 等 V6 校准 |
| 40 轮够完成任务 (运行 002 从 15 轮改成 40 轮时的判断) | 002-004 的测试在第 30-39 轮才通过, 40 轮用完时都还在做验证, 三次都没有交出报告 | 改成按 token 计算的预算, 并留出收尾的余量 |
| 每轮的 token 用量很难预测 | 用"上一轮的增长量"预测, 误差的中位数不到 2%, 最大 33% | 预算用简单的预测, 由收尾阶段留出余量 |
| 用到 80% 时开始收尾 (模块 3 最初的设计) | 用 003, 004 的真实用量回放: 预算 50 万时, 80% 之后一轮收尾都没有. 剩下的百分比能做几轮, 取决于每轮有多贵 | 改成"按现在的消耗, 剩下大约 5 轮时收尾", 和预算的大小无关 |
| "已经用掉的 + 这一轮 > 预算"时, 这一轮就是最后一轮 (模块 3 最初的设计) | 回放发现最后一轮正好超出预算: 最后一轮本身也要消耗 token | 改成"这一轮做完, 还放不放得下下一轮". 回放 2 次运行 × 3 种预算, 都没有超出, 用掉 92% 到 100% |

**决定**

1. **每个参数都要写明来源**, 来源只有三种:
   - **数据**: 来自哪几次运行, 统计的是什么 (例如"003, 004 单轮输出最多 2370 tokens");
   - **推导**: 从别的数据或约束推出来 (例如"80% 开始收尾: 预测的最大误差是 33%, 留出的余量要能兜住一次大的误差");
   - **暂定**: 还没有数据, 必须写明以后怎样校准 (一般是 V6).
   没有来源的数字不允许出现. 来源写在定义参数的那一行注释里, 暂定的参数在注释里写明"暂定".
2. **设计也一样**: 要不要做一个功能 (比如某个护栏), 先用 trace 统计这个问题出现了几次, 危害有多大, 再决定. V5 的三个护栏都是这样选出来的, 没选上的也写明了原因.
3. **数据不够时, 用最简单的做法**, 不要用一个看起来很科学的公式掩盖拍脑袋. 简单的做法至少是诚实的, 以后有了数据也容易替换.
4. **参数都记进运行记录**: 配置 (`settings`), 护栏 (`guards`), 预算 (`budget`) 都写进 meta. 两次运行的结果不同时, 要能分清是哪个条件不同.
5. **V6 负责把"暂定"变成"数据"**: 同一道题跑多次, 看分布, 画出"参数和通过率"的曲线 (比如预算和通过率), 再定默认值.

**现在的参数** (V5 模块 3 之后)

| 参数 | 值 | 来源 | 依据 |
|---|---|---|---|
| `max_tokens` (单轮输出上限) | 8192 | 数据 | 003, 004 单轮输出最多 2370 tokens, 有 3.5 倍余量, 一次都没有被截断 |
| `token_budget` (预算) | 200 万 | 暂定 | 003, 004 测试通过时分别用了 122 万和 109 万, 但都还没有做完验证. 只有 2 次运行, V6 校准 |
| 开始收尾 | 剩下约 5 轮时 | 推导 + 数据 | 收尾要跑一遍测试, 修一处小问题, 再跑一遍, 写报告, 约 5 轮. 用 003, 004 的用量回放 (预算 50 万, 100 万, 120 万): 都在最后一轮之前收尾 3 到 4 轮, 没有一次超出预算 |
| 中途提醒 | 50% | 暂定 | 只是让 agent 知道进度, 没有数据. V6 对比"提醒和不提醒" |
| `max_turns` (轮数上限) | 80 | 推导 | 只作为断路器, 不应该触发: 按 003, 004 的增长速度推算, 200 万的预算大约在第 45 到 53 轮用完, 80 留出了余量 |
| 测试节奏的提醒 | 每 6 次修改 | 数据 | 003, 004 连续修改的阶段都在 10 轮以上, 6 次会在中间提醒一次 |
| 重复调用 | 第 2 次提醒, 第 3 次拦下 | 暂定 | 003, 004 的重复都只有 2 次, 没有出现过第 3 次. 拦下的门槛定得保守 |
| `command_timeout` (命令超时) | 60 秒 | 数据 (只限 cortex) | 003, 004 最慢的命令 1.1 秒. 换一个测试慢的仓库就不成立, 以后按题目设置 |
| `max_output_chars` (工具结果上限) | 20000 字符 | 暂定 | 003, 004 各碰到过一次上限. 定在多少合适, 要看截断之后模型是否需要重新读取 |
| `MAX_CONSECUTIVE_TRUNCATIONS` | 3 | 暂定 | 到现在为止没有出现过被截断的回复 |
| `llm_max_retries` / `llm_timeout` | 3 次 / 300 秒 | 暂定 | 到现在为止没有出现过调用失败, 用的是 SDK 的常见设置 |

**理由**

- **可解释, 可复现**: 每个数字都能回答"为什么是这个值". 评审代码, 或者以后推翻某个决定时, 有据可查;
- **防止规则越堆越多**: 凭直觉加的规则, 很难说清楚什么时候可以删掉. 有数据的规则, 数据变了就知道该改了;
- **直觉经常是错的**: 上面的表里, 7 次凭直觉的判断, 每一次都被数据修正了 (有的是判断错了, 有的是问题没有想象的那么难). 其中 2 次是同一个模块里的设计 (预算), 单元测试全部通过, 只有用真实数据回放才发现.

**代价**

- 慢: 每个决定都要先统计, 有时还要先跑一次运行;
- **数据只来自 1 道题**: 现在所有"数据"类的参数, 都只在 cortex 上成立. 在一道题上调好的参数, 换一道题不一定好, 这和模型在训练集上过拟合是同一个问题. V6 要在多道题上校准, 而且要像 V7 那样分开"用来定参数的题"和"用来检验的题";
- 有些参数很难拿到数据 (比如调用模型失败时的重试次数), 只能长期标为暂定.

## ADR-019 护栏, 预算和交给人 (V5)

**背景**
运行 002-004 暴露出一组"做事方法"上的问题, 都不是改 prompt 能解决的 (prompt 里写了, 三次都没有照做):

- 三次都在 40 轮用完时停下, **没有一次交出最终报告**, 人只能自己去翻 diff;
- `pytest | tail` 显示退出码 0, 实际上 pytest 失败了 (004 第 1 轮, 退出码 4);
- 测试只在开头和最后几轮运行, 003 在第 1 轮和第 39 轮之间修改了 21 轮;
- 002 在测试通过之后擅自做了一个全局的修改 (给模型加 `coerce_numbers_to_str`), 引入了所有测试都发现不了的缺陷. 这本该交给人决定;
- "交给人"靠模型在第一行写"需要人工处理", loop 用字符串匹配识别, 既脆弱, 也带不了结构化的信息.

**决定**

1. **护栏** (`harness/guards/`): 在 loop 里观察 agent 的行为, 必要时提醒或拦下.
   - 和权限策略的区别: 策略管"能不能做" (安全), 静态, 出错时拒绝 (fail-closed); 护栏管"做得好不好", 有状态, 大多数时候只提醒, 出错时去掉这个护栏, 运行继续 (fail-open);
   - 三个钩子: before_turn (调用模型之前), before_call (执行工具之前, 可以拦下), after_call (执行工具之后, 在结果末尾追加提醒). 顺序是: 权限策略 → before_call → 执行 → after_call. 被策略拒绝的调用不会交给护栏;
   - 护栏只能提醒或拦下, **不能改写模型的调用**; 交给护栏的参数是深拷贝 (frozen 的 dataclass 管不到 dict 里面的内容);
   - 三个护栏都来自 trace 的统计 (ADR-018): pipe_exit_code (管道的退出码是 0 时提醒), repeat (完全相同的调用和结果, 中间状态没变过: 第 2 次提醒, 第 3 次拦下), test_cadence (上次跑测试之后修改了 6 次, 提醒跑测试). 宁可漏报, 不要误报: 护栏的误报会打断正常的工作.
2. **预算** (`harness/budget.py`): 按"模型处理的 token 总量"计算, 而不是按轮数.
   - 轮数不是成本的单位: 每一轮都要重发全部历史, 004 最后 10 轮占了总量的 37%;
   - **预算是无状态的**: 需要的数字都在 loop 交给它的账本 (`Usage`) 里, 而账本的数字就是接口返回的真实用量. 以后从检查点恢复时, 只需要恢复 loop 的状态;
   - 用"上一轮的增长量"预测下一轮, 不需要自己数 token;
   - 第 1 轮告知预算; 剩下大约 5 轮时进入收尾 (不是 80%: 回放发现百分比不能随预算的大小缩放); "这一轮做完, 放不下下一轮"时, 这一轮是最后一轮 (不是"这一轮放不下": 回放发现那样会超出预算). 两处都是用 003, 004 的真实用量回放发现的, 单元测试没有发现;
   - 最后一轮传 `tool_choice: none`, 并附上提醒. 实际验证过 (docs/v5/tool-choice-check.md): 只有 none 不够, DeepSeek 会把工具调用当成文字写出来, 必须和提醒一起用;
   - 轮数上限 (80) 只作为断路器; 预算的默认值 (200 万) 属于配置, 题目里可以单独设置.
3. **交给人** (`tools/handoff.py`): escalate 工具, 参数是结构化的 (类别, 卡在哪里, 需要人做什么决定, 可选的做法, 试过什么, 现在的状态).
   - 工具结果里带一个**控制信号** (`ToolResult.handoff`), loop 读字段决定停下, 而不是解析模型写的文字;
   - 先把这一轮的工具结果写进历史再停下, 同一条回复里排在后面的调用不执行, 但也给出结果: 历史停在一个完整的状态;
   - 旧的文字标记保留, 兼容 system_v1, v2.
4. **system_v3**: 只改 V5 的新机制必须改的地方 (harness 的提醒是什么, 什么时候交给人, 收尾做什么), 并修正了 cmd.exe 的说明 (原来写"没有 tail", 在这台机器上是错的). **只写通用的原则, 不写某一道题的具体问题**: 测试会检查模板里没有 pydantic, coerce_numbers_to_str 这类词.
5. **有意不做的**: "没有进展"的检测 (003, 004 里没有进展的时段全部是正常的探索和验证, 见已知的局限); 上下文压缩 (主题不同, 和护栏一起上线会分不清谁的效果, 放进 V7).

**结果** (运行 005, [记录](v5/runs/005-cortex.md))

| | 004 | 005 |
|---|---|---|
| 停止方式 | max_turns, 没有报告 | **finished, 交出了完整的报告** |
| 测试全部通过 | 第 32 轮 | 第 24 轮 |
| 运行测试的次数 | 3 | 5 |
| 收尾 | — | 第 36 轮进入收尾, 之后没有再修改, 跑测试, 写报告 |
| 护栏 | — | 触发 1 次 (管道掩盖了退出码), 下一轮就改正了; 没有误报 |
| 评分 | FAIL (别名) | FAIL (别名, 和 004 相同) |

评分没有变化: V5 改变的是"怎样工作", 不是"知道什么". 别名的问题第 4 次被漏掉, 是 V7 (经验与记忆) 要验证的问题.

**理由**

- 这些问题 prompt 改不掉, 只能在 harness 里用代码保证 (和权限策略"在代码里强制执行, 在提示词里告知模型"是同一个思路);
- 每个机制都能在 trace 里单独看到它的作用 (每次提醒, 拦下, 收尾, 交给人都是一个事件), 不需要只靠最后的结果去猜.

**代价**

- **005 评估的是 V5 整体**: prompt, 护栏, 预算一起改了, 只看结果分不清各自的作用. 按事件逐条分析能看出一部分 (收尾和 pipe_exit_code 的作用很清楚; test_cadence 没有触发, 测试跑得更勤不是它的功劳), 严格的消融实验留给 V6;
- **只有一次运行, 而且是在调 prompt 用的那道题上**: v2, v3 都是根据这道题上暴露的问题写的, 002-005 的结果都偏向这道题. 005 还用了官方的 codemod (002-004 都没有), 这个变化无法归因. V6 要在多道题上各跑多次, 并且区分"用来调 prompt 的题"和"用来检验的题";
- 护栏和 grader 一样只适配 pytest;
- escalate 的界线不清楚: 005 把一个"很难判断哪一种行为是对的"问题写进了报告, 而不是交给人 (这次的处理其实是合理的);
- 护栏的提醒追加在工具结果的末尾, 仓库里的文件也可能包含同样的前缀, prompt 只能靠位置区分. 更可靠的做法是在 harness 里处理工具输出中出现的前缀, 留给以后.

## ADR-020 先搭好框架, 最后统一评测; 沙箱提前到评测之前

**背景**
V5 之后原来的顺序是 V6 评测 → V7 经验与记忆 → V8 统一接口 → V9 沙箱. 讨论 V6 时发现两个问题:

1. "评测"其实是两件事: **评测框架** (批量运行, 汇总指标, 对比两种配置, 生成报告) 是代码, 几乎不花钱, 可以用假模型和已有的 trace 验证;
   **评测战役** (准备好题库, 每道题跑很多次) 才是花钱最多的部分. 原来的安排把两者绑在一起, 每个版本都要重新跑一轮评测, 钱要花好几次,
   而且不同版本得出的数字来自不同的系统, 不能放在一起比较;
2. **沙箱排在最后是不对的**: 评测要批量地, 无人值守地运行很多次, 而本地环境的约束是"只能用于可信的仓库, 运行时要有人观察" (ADR-009).
   另外, grader 最大的漏洞 (agent 改了 venv, grader 看不到; 被测代码能篡改检查的结果) 的根本解决办法也在沙箱里: 在全新的工作区上重放 diff 再评分 (ADR-017).
   运行 005 里, agent 已经往 venv 里装了别的包, 这个漏洞不是假想的.

**决定**

新的顺序 (版本号保持不变, 只作为名字: 代码注释和文档里大量引用了 V7, V9 这些编号, 改编号的代价比顺序和编号不一致更大):

| 顺序 | 版本 | 内容 | 验证方式 |
|---|---|---|---|
| 1 | V6 评测框架 | 批量运行, 汇总指标, 对比配置, 生成报告 | 假模型; 用 002-005 已有的记录生成第一份报告 |
| 2 | V9 沙箱 | Docker 的环境和工作区, 关闭网络; 在全新的工作区上重放 diff 再评分 | 在容器里重新评 005, 和本地的结论对比 |
| 3 | V7 经验与记忆 | 工作记忆 (上下文压缩) 和长期记忆 | 1 到 2 次真实运行 |
| 4 | V8 统一接口 | 对外的调用方式 | 假模型 |
| 5 | 题库和最终评测 | 多道题; 有记忆, 没有记忆分别跑多次 (消融实验) | 这就是最终的测试, 用来定参数, 也是简历上的数字的来源 |

- **每个版本只做最小的验证**: 假模型, 回放已有的 trace, 或者 1 到 2 次便宜的真实运行. 避免大爆炸式的集成: V5 的预算, 单元测试全部通过, 用真实数据回放才发现了两个设计错误;
- **最终评测全部用同一个版本的 harness** (同一个 commit, 写进每次运行的 meta), 结果才能放在一起比较;
- **最终评测也分阶段**: 先用 1 道题跑 1 次做冒烟测试, 确认整条流水线没有问题, 再扩大规模, 避免一次花掉大量的钱才发现某个环节坏了;
- **题库的准备** (找仓库, 确认基线, 整理隐藏测试) 不涉及代码, 可以随时穿插进行;
- 和 ADR-016 不冲突: V7 依然排在评测框架之后, 小规模的检查可以直接用 V6 的框架; 证明记忆有用的消融实验在最终评测里做.

**理由**

- 钱只花一次, 最终的数字来自同一个系统;
- 沙箱是无人值守批量运行的前提, 也是让 grader 可信的前提, 应该在大规模运行之前完成;
- 框架先搭好, 最终评测时如果发现某个参数需要调整, 不用再改代码结构, 只需要改配置再跑.

**代价**

- **V7 的设计只有很少的数据**: 记忆写什么, 什么时候取出, 只能先按少量运行的数据定, 都标为暂定 (ADR-018), 在最终评测里校准;
- **问题发现得晚**: 最终评测里才暴露的问题, 要回头修改已经写完的版本. 用"每个版本做最小的验证"来降低这个风险, 但不能消除;
- **沙箱提前, Docker 在 Windows 上的调试成本也提前了**: 如果遇到很难解决的问题 (比如 Docker Desktop 的文件挂载性能), 需要重新评估, 或者先用 WSL.

## ADR-021 评测框架 (V6)

**背景**
到 V5 为止, 每次判断"这个改动有没有用", 都只有一次运行, 而且是手工对比. 003 的记录里就看到过: 同样的条件, 两次运行的过程差别很大.
V7 要证明"有记忆比没有记忆好", 需要在多道题上各跑多次, 并且能说清楚这个差别是不是运气. ADR-020 把评测分成两件事:
框架 (代码, 现在做) 和最终评测 (花钱, 最后做). 这条记录的是框架.

**决定**

1. **指标只从 trace 提取** (`evaluation/records.py`): 一次运行 → 一个 `RunRecord` (状态, 评分, 每项检查, 有没有交报告, 测试通过的轮次, 跑测试的次数, token, 护栏和交给人的次数, harness 和 prompt 的版本).
   - 批量运行时和事后重新统计, 得出的数字完全一样; 旧的运行 (003, 004) 也能直接统计;
   - 运行记录的格式一直在变, 每个字段都要处理"旧记录里没有它"的情况 (模式演进); **None 和 0 分开**: 没有评分不等于不通过;
   - "测试全部通过"要同时满足: 退出码 0, 有 passed, 没有 failed / error. 只看退出码会被管道骗 (004 第 1 轮);
   - 用 003-005 的真实 trace 检验: 测试通过的轮次 (39, 32, 24), 跑测试的次数 (2, 3, 5) 和人工统计的完全一致.
2. **统计** (`evaluation/stats.py`):
   - 一次运行的结果分四种: pass, fail, invalid (准备失败, 崩溃, 调用模型失败, 被打断: 不是 agent 的成绩), ungraded. 后两种不计入分母, 但数量要报告;
   - 通过率用 **Wilson 区间**, 不用 Wald 区间: 样本小, 比例接近 0 或 1 时 Wald 区间是错的 (5 次全部通过, Wald 区间的宽度是 0);
   - **pass@k 用无偏估计** 1 - C(n-c, k) / C(n, k) (Chen et al., 2021), 跨题目时先按题目算再平均 (宏平均);
   - 两组的差用 **Newcombe 区间** (由两个 Wilson 区间组合而成), 区间跨过 0 就是"还分不出好坏". 和文献中的例子核对过, 一位不差;
   - 推算出最终评测的规模: 真实的通过率 40% 对 80% 时, 每组大约要 11 次才能分出好坏; 50% 对 70% 要 41 次.
3. **对照组** (`runner.AgentConfig`, `evaluation/spec.py`):
   - 题目描述"做什么", AgentConfig 描述"怎样做" (prompt 的版本, 护栏, 预算, 轮数上限), 两者分开, 同一道题才能用不同的配置去跑. 默认值就是标准配置, 原来的调用都不用改;
   - 预算的优先级: 对照组 > 题目 > 配置的默认值;
   - 实验文件 (`experiments/*.toml`) 是声明式的数据, **在花钱之前做完所有的校验**: 护栏或 prompt 的名字写错, prompt 和现在的变量对不上 (真的渲染一次), 题目不存在或者没有评测信息, 都在第一次运行之前报错;
   - 整个实验的 token 上限没有默认值, 必须明确写出来;
   - **运行计划交错排列** (A B A B, 而不是 A A B B): 服务商那边的变化 (模型更新, 某段时间慢) 平均地落在每一组上, 而不是变成两组之间的"差别" (区组化). 提前停下时, 已经完成的部分在各组之间也是平衡的.
4. **批量运行** (`evaluation/batch.py`):
   - 清单 (manifest.jsonl) 只追加, 每行立刻写盘, 和 trace 的事件流一样: 崩溃时已经完成的运行都在;
   - **中断后可以接着跑, 而且是幂等的**: 已经完成的运行直接跳过; 完成了的实验再启动一次, 什么都不做. 接着跑之前核对: 实验的定义和 harness 的版本都不能变 (ADR-020), 除非明确加上 `--allow-version-change`;
   - 无效的运行当场重试一次, 还是失败就放弃这一次 (作为 invalid 计数);
   - 整个实验的上限: 每次运行开始之前, 已经用掉的 + 这次运行的**预算** > 上限, 就不再开始. 用预算而不是平均用量: V5 保证一次运行不超出预算, 所以整个实验也不会超出上限;
   - harness 崩溃时停下整个实验: 有 bug 时继续跑, 结果不可信, 钱也白花;
   - **评测时给所有 agent 运行过的结果评分** (budget, max_turns 也评分): 只给 finished 评分, 通过率就只来自"做完了的那些", 会被高估 (幸存者偏差). 这改变了 ADR-017 里"只给 finished 自动评分"的决定, 平时手动运行时不变;
   - 创建模型客户端的函数从外面传进来 (依赖注入): 测试用假模型, 一分钱不花; 每个对照组可以用不同的模型.
5. **报告** (`evaluation/report.py`): **局限写在最前面** (混用了不同版本的 harness, 样本小, 有无效或没有评分的运行), 先知道数字有多可信, 再看数字. 报告只依赖 RunRecord, 实验和零散的旧运行都能生成报告.
6. **命令行**: `eval run` 和 `eval report`. 本地环境里批量运行 (多于 1 次) 必须加 `--allow-local`: 把 ADR-009 的"运行时要有人观察"写进代码.

**结果**

- 用 003-005 生成了第一份报告 ([report-003-005](v6/report-003-005.md)): system_v2 和 v3 的差是 +0% [-66%, +79%], 还分不出好坏. 这 3 次运行只用来检验报告本身;
- 冒烟测试 ([记录](v6/runs/smoke.md)): 整条流水线端到端走通. harness 是干净的; 第 41 轮收尾, 第 45 轮最后一轮写出了正常的报告, 用了预算的 98.7%, 没有超出. 和 005 的配置相同, 过程差别很大 (一次用 codemod, 一次自己写脚本), 评分都是 FAIL (别名, 第 5 次).

**理由**

- 每个统计方法的选择, 都是因为我们的样本小, 比例常常是 0 或 1: 这正是常见的简单方法 (Wald 区间, 有放回的 pass@k, 看区间是否重叠) 出错的地方;
- 幂等, 只追加的清单, 版本核对: 长时间的批量任务里, 中断和重启是常态, 结果还要能放在一起比较.

**代价**

- **只能顺序运行**: 一次 cortex 的运行要 3 分钟左右, 再加上评分时准备旧版本的环境. 并行运行需要互相隔离的环境, 和 V9 的沙箱一起做;
- **每次评分都要准备一次旧版本的环境** (约 25 秒, 28 MB): 评测时每次运行都评分, 这个代价放大了. 按题目缓存旧版本的接口表面;
- **一次运行很贵**: cortex 一次 180 万到 200 万 tokens. 想分出中等程度的差别, 每组要跑几十次. 最终评测需要更便宜的题目;
- **统计方法假设每次运行互相独立**: 同一道题的多次运行其实相关 (题目的难度相同), 跨题目时用宏平均缓解, 但区间仍然偏乐观;
- 报告里的 pass@k 只在每道题跑的次数不少于 k 时才有意义.

V6 完成后, 按 ADR-020 下一步是 V9 沙箱. 但有一位老师想看这个项目的测试结果, 而沙箱 (Docker 的镜像, 断网, 在全新的工作区上重放 diff 再评分) 对"测试结果"本身没有直接的贡献.

## ADR-023 上下文视图只做到规则, 先不接进 loop

**背景**
V7 的第一部分是工作记忆. 数据显示, 003-005 和冒烟测试最后一轮的上下文里, 有很大一部分已经没用了: 读过之后又被修改的文件,
被新的结果取代的测试输出, 很长的搜索结果. 于是设计了"上下文视图": 记录 (完整的历史) 和视图 (每一轮发给模型的上下文) 分开,
逐项判断哪些丢掉, 压缩, 原样保留, 判断单调, 攒一批再生效以保护缓存. 步骤 1a (规则, 纯函数) 写完之后,
讨论了一个问题: 这件事对我们真正关心的东西 (成功率, 以及 Growth) 有多大的帮助?

**决定**
- 步骤 1a 的规则 (`harness/context.py`) 保留: 纯函数, 有测试, 没有接进 loop, 不影响任何行为;
- 1b (单调, 合并, 生成视图), 1c (接进 loop), 1d (回放定参数) **暂停**;
- V7 的重点转到长期记忆: 从做过的任务里积累经验, 以及怎样把经验放进上下文.

**理由** (ADR-018: 先用数据证明问题存在, 再决定做不做. 这一次是用它来决定"不做什么")
- **失败的原因不在上下文**: 5 次运行, 原有的测试全部通过, 废弃警告和旧写法都清理干净了, 唯一的失败每次都一样: 别名.
  这是"不知道"一个行为变化, 而不是"被过期的内容误导". trace 里也没有找到 agent 照着旧的文件内容改错的例子;
- **费用不是问题**: 一次升级约 200 万 tokens, 95% 以上命中缓存. 和人工迁移的时间相比可以忽略; 真实的使用场景里, 一次升级也只运行一次;
- **上下文还没到极限**: 最后一轮 65K 到 78K tokens, 在模型的窗口之内;
- "模型一直看着过期的内容"只是一个合理的推测, 没有数据证明它影响了结果. 规则能省下 36% 到 41% 的工具结果, 这一点是真的, 但省下来的部分对成功率的影响还不知道.

**什么时候重新考虑** (最终评测时都可以自动统计)
- 更大的仓库: 上下文接近模型的窗口上限;
- trace 里出现了被旧内容误导的错误 (比如照着过期的文件内容去改, edit_file 找不到原文);
- 有不少运行因为预算用完而失败, 而且失败的原因是"还没做完", 不是"做错了".

**代价**
- 已经写好的规则暂时用不上. 它们是纯函数, 维护的代价很小;
- 如果以后要做, 1b 里"单调, 合并"的设计要重新确认一遍 (缓存的实际表现, 更早轮次的 thinking 能不能省略), 那时会有真实的数据.

## ADR-024 长期记忆: 经验卡片, 推送和自己查, agent 自己提炼, 用证据代替审核

**背景**
002, 003, 004, 005 和冒烟测试, 5 次运行都漏掉了同一个问题: pydantic 2 里, 带别名的字段默认不能再用字段名赋值.
V5 改变了 agent "怎样工作" (交报告, 跑测试, 收尾), 改变不了它"知道什么". 003 第 11 轮的思考甚至写着"Field(None, alias='class') 照样能用":
它对自己的判断很有信心, 只是判断错了. 每次运行都从零开始, 第 6 次还会漏掉. 这就是项目名字里 Growth 要解决的问题.

**决定**

1. **一条经验是一张卡片** (`memories/<id>.toml`, 和题目一样是数据, 提交, 可以审查):
   - 适用范围: 依赖, 版本 (主版本号, 比如 1 → 2);
   - 两种触发条件, 都由模型在提炼时写出: **机器的** (`trigger.grep`, 一个正则表达式, harness 在工作区里执行), **语义的** (`applies_when`, 一句话, 给模型自己判断);
   - 内容: 症状, 为什么测试发现不了, 做法, 怎样验证;
   - 证据 (从哪道题, 哪几次运行, 哪项检查学到的, 谁写的): **只给人和 harness 看, 永远不进 prompt**;
   - **写成库本身的行为, 不写某个仓库的细节**: 否则换一个仓库就没用了, 再拿学到它的那道题评测, 等于告诉了答案.
2. **推送和自己查, 两种方式一起用**, 失败的方式正好互补:
   - 推送 (精确): 准备阶段结束后, harness 在工作区里执行每张卡片的 `trigger.grep`, 只有匹配的才会被用到. 开始时在任务消息里给一个**目录** (每张一行);
     agent 读到匹配触发条件的文件时, 附上这张卡片的**完整内容** (每张只给一次, 和护栏的提醒是同一个机制); 测试第一次全部通过时, 提醒还没有处理的卡片;
   - 自己查 (不漏): `list_experience` (这个依赖的全部经验, 包括没有被触发的), `recall_experience` (一张卡片的完整内容);
   - **去掉要有证据** (`dismiss_experience`): 必须附上这次运行里执行过的验证命令, harness 检查它确实执行过. 只说"我觉得无关"会被拒绝.
     理由就是 003 第 11 轮: 模型最自信的地方, 恰恰是它错了的地方. 这和 ADR-017 是同一个原则: 不相信 agent 的说法, 只看证据.
3. **经验由 agent 自己提炼** (反思, Reflexion, Shinn et al., 2023): 每次运行评完分之后, 单独调用一次模型, 输入是评分报告, agent 的最终报告和 trace 的摘要, 输出是卡片格式的草稿.
   人的角色是监督, 不是生产: 抽查, 以及收到告警时查看.
4. **用证据代替逐条审核**, 卡片有一个生命周期:
   - draft (刚提炼出来, **不会被使用**) → validated (在学到它的题目上带着它重跑一次, 原来失败的那项检查通过了) → deprecated (用了以后成功率下降, 确认是坏的);
   - 在同一道题上验证, 只能证明"它是对的, 而且 agent 能照着做", 不能证明它能迁移; 迁移要靠消融实验.
5. **统计从 trace 里来, 不写回卡片**: 每张卡片被推送, 查看, 去掉了几次, 用了以后结果怎样, 都从每次运行的记录里算出来 (和 RunRecord 一样, 只有一条事实来源).
   "被去掉, 但最后那一项检查失败了"是最危险的信号: agent 判断错了, 这条经验其实是对的.
6. **由代码强制执行的保护**:
   - **评测时, 自动排除从当前这道题学到的经验** (`evidence.learned_from`);
   - 卡片里不能出现原仓库的细节 (文件路径, 类名, 隐藏测试的名字), 提炼时自动检查, 出现了就退回重写;
   - 模型写的触发条件要检查: 正则能编译, 在学到它的那个仓库里能匹配上;
   - 适用条件相同的经验要合并, 证据累加, 不另起一张;
   - 记忆是有版本的 (全部有效的卡片的哈希), 写进每次运行的 meta. 出了问题可以回滚到上一个版本.

**分层**: `memory/` (卡片的格式, 存储, 选择, 一次运行里的状态) 在最下面, 只依赖 config; 工具 (`tools/experience.py`) 和推送 (harness 的护栏) 依赖它;
runner 负责选卡片, 记进 meta; 提炼和验证要调用模型, 要重跑, 放在最上面的 `learning/` (在 evaluation 之上).

**理由**
- 卡片的结构让每一步都可以由机器检查: 触发条件可以执行, 验证可以执行, 证据可以统计;
- 推送解决"模型想不到去查" (我们的数据: prompt 里写明的要求, 它经常不照做), 自己查解决"触发条件漏掉了";
- 错误的经验比没有经验更糟 (002 的全局修改如果被记成经验, 以后每次都会引入同一个缺陷), 所以 draft 不会被使用, 去掉要证据, 坏的经验能被发现和回滚.

**代价**
- **训练的信号来自隐藏测试**: 真实的业务里没有隐藏测试, 学习的信号要来自 PR 的审核意见, 合并后 CI 的失败, 或者 agent 自己的行为检查. 现阶段用带隐藏测试的题目训练, 相当于有标注的数据;
- 验证要重跑一次 (约 200 万 tokens), 不便宜;
- 反思由模型完成, 提炼的质量要靠验证和监控兜底, 一开始可能需要多次抽查;
- 推送依赖正则表达式, 只能识别代码里的写法, 识别不了更复杂的语义 (比如"这个字段在运行时被动态赋值"), 这部分靠自己查补上.

## ADR-025 长期记忆的实现 (V7): 和设计不一样的地方

**背景**
ADR-024 是长期记忆的设计. 实现的过程中, 有几处被测试和数据推翻了, 或者需要补上设计里没有想到的东西. 这条记录写下实现了什么, 以及每一处改动的原因.

**实现了什么**

| 部分 | 代码 | 内容 |
|---|---|---|
| 卡片 | `memory/card.py`, `memory/store.py` | 格式, 校验, 读写 (往返一致), 按依赖和主版本号筛选, 排除学到它的题目, 记忆的版本号 |
| 匹配 | `memory/match.py` | 触发条件在工作区里匹配, 每张卡片一个子进程, 限时 |
| 一次运行里的状态 | `memory/session.py` | 匹配上, 推送, 查看, 去掉了哪些; 去掉的证据 |
| 推送 | `harness/guards/experience.py` | 读到匹配上的文件时给出完整内容; 测试第一次全部通过后提醒逐条检查 |
| 自己查 | `tools/experience.py` | list_experience, recall_experience, dismiss_experience (要证据) |
| 接进 runner | `runner/run.py`, `prompts/task_v2.md` | `AgentConfig.memory` (默认关闭), 任务消息里的目录, 记进 meta |
| 反思 | `learning/reflect.py`, `learning/checks.py`, `prompts/reflect_v1.md` | 由模型提炼草稿, 自动检查, 合并 |
| 验证 | `learning/validate.py` | 在学到它的题目上带着它重跑, 失败的检查通过了才升级 |
| 统计和告警 | `evaluation/report.py` | 每张卡片的推送, 查看, 去掉的次数, 用到时和没用到时的通过率; "去掉之后没有通过"的告警 |
| 命令行 | `cli/memory.py` | list, show, reflect, validate, set-status |

**和 ADR-024 不一样的地方**

1. **ReDoS 的防线: 从"检查写法"改成"进程限时"**. 原来的设计是加载时拒绝嵌套的量词, 匹配时每行只看 500 个字符.
   写测试时用了 `a.*a.*a.*b`, 测试卡住了好几分钟: 它没有嵌套的量词, 匹配 300 个字符就要 0.4 秒, 而且随长度多项式增长.
   检查写法永远列不全所有危险的写法 (和 ADR-009 的黑名单是同一个道理), 所以改成每张卡片在单独的进程里匹配, 超过 10 秒就杀掉.
   检查写法保留, 作为便宜的第一道防线;
2. **推送改成按文件的路径判断**, 不在 agent 循环里执行正则. 原来的设计是 agent 每读一个文件, 就用正则匹配内容.
   运行开始时已经在子进程里扫描过整个仓库, 推送只需要判断"读的这个文件在不在匹配上的文件里". 代价是 agent 自己新建的文件不会触发推送, 由"自己查"补上;
3. **评分报告里加上了隐藏测试的报错** (`failure_messages`). 反思要知道"为什么"失败 (比如 `assert None == 100`), 而不只是"哪个测试"失败了. 这是训练时的老师的反馈, 只给人和反思看;
4. **记忆的版本号只由会影响 agent 行为的部分决定**: 给 agent 看的内容, 触发条件, learned_from. 证据里的其他字段 (source_runs 等) 不算: 合并经验时证据会累加, agent 看到的内容没变, 版本号也不应该变;
5. **经验的工具只在有可以用的经验时注册**; **没有匹配上任何经验时, 任务消息依然用 task_v1**. 这样"有记忆但没有匹配上"和"没有记忆"的运行, 看到的任务消息完全一样;
6. **验证模式** (`AgentConfig.memory_cards`): 只用指定的卡片, 不管状态, 不排除学到它的题目. 只用于验证, **实验文件 (ArmSpec) 没有这个字段, 评测不可能用到它**; 验证用的运行在 meta 里写明 `forced`, 报告会单独标出;
7. **反思时, 适用范围, 状态, 证据由 harness 填写**, 模型只写内容和触发条件: 不让模型决定"这条经验从哪道题学到的", 否则排除规则可以被绕过.

**理由**
- 第 1, 2 点: 触发条件是模型写的, 是不可信的输入. 可靠的边界只能来自操作系统 (进程可以被杀掉), 而且不可信的东西不应该在关键路径 (agent 循环) 上执行;
- 第 5, 6 点: 消融实验要求两组之间只差一个变量, 验证要求不能污染评测.

**代价**
- 一次运行里的经验状态 (`ExperienceSession`) 没有放进 loop 的 `_Run`, 不符合"状态外置"的原则. 以后要从检查点恢复运行时, 要一起恢复;
- "原仓库的细节"只检查了文件路径, 类名, 测试的名字, 题目和仓库的名字. 字段名, 函数名这类细节还检查不出来;
- 反思和验证都**还没有在真实的数据上跑过** (要花钱): 反思写出的经验质量如何, 验证能不能让失败的检查通过, 都还不知道;
- 验证只能证明"在学到它的题目上有用", 证明能迁移, 要等第二道题和消融实验.

## ADR-026 对比实验, 经验必须明确处理, 反思看迁移之前的类

**背景**
第一次真实的反思和验证 (docs/v7/reflection-check.md, docs/v7/validation-001.md): 经验的三个投递渠道都工作了, agent 也照着卡片做了实验, 而且实验看到了 bug, 但最后的结论错了, 隐藏测试和没有经验时一样失败. trace 里能看出三个原因:
1. 卡片的适用条件写错了 ("v1 用了 allow_population_by_field_name"), 而这个仓库没有用. agent 照着条件去找, 没找到, 就判断"不适用";
2. agent 想在旧版本上验证 (第 44 轮的思考: "let me verify empirically whether v1 allowed..."), 但旧版本已经被升级掉, 权限策略也不允许改回去. 它只好凭记忆推断旧版本的行为, 推错了. V0 的人工迁移正是靠在旧版本上做同样的实验, 才发现了这个问题;
3. agent 在报告里写了"不适用", 却没有调用 dismiss_experience: 统计里看不到这次拒绝, "去掉之后失败了"的告警也不会出现.

**决定**
1. **对比实验 (`tools/probe.py`, `compare_versions`)**: 准备流水线在基线测试之后, 再建一个只装了旧版本目标依赖的虚拟环境 (`.venv-baseline`). 工具把同一个脚本在新旧两个环境里各运行一次, 两边都用 `python -I`, 结果放在一起. 对比环境只装目标依赖, 不装仓库: 实验要回答的是"库的行为变了没有". 对照组可以关掉它 (`compare_versions = false`), 用来做消融;
2. **交给 agent 的每一条经验都要明确处理**: 新增 `confirm_experience` (适用, 已经处理), 和 `dismiss_experience` 一样必须附上执行过的验证命令, 对比实验也算. 两者都没有的, 记为"未处理" (`unresolved`). 报告增加"确认", "未处理"两列, 以及"未处理而失败", "确认了而失败"两种告警. 任务消息换成 task_v3, 测试通过时的清单要求用这两个工具处理;
3. **reflect_v3**: 给反思的代码证据, 从"字段那一行 (迁移之后)"改成"迁移之前, 报错里的名字所在的类的完整定义" (包括嵌套的 `class Config`). prompt 要求适用条件必须能在旧代码里看到, 写出旧版本下的实际行为, `verify` 写成新旧版本的对比实验. 触发条件也改为在迁移之前的代码上检查.

**理由**
- 迁移的核心问题是"行为变了没有", 只能在新版本下做实验的 agent, 永远只看到一半. 这是能力的缺失, 不是 prompt 能补上的;
- 统计只认工具调用, 用文字表达的决定必须变成工具调用, 否则监控 (ADR-024: 用监控代替逐条审核) 就有盲区;
- 卡片的错误来自反思时看到的信息不够 (看不到 `extra='allow'`), 而不是模型不够聪明: 先补信息.

**代价**
- 准备流水线多了一个虚拟环境和一次 pip install (几秒到几十秒), 也多了一个网络依赖;
- 对比环境里没有仓库的代码: 实验脚本要自己定义需要的类. 要用仓库自己的代码在旧版本下做实验, 需要完整地再装一次, 现在不做;
- agent 的工具变了, harness 的版本也变了: 之前的运行和之后的不能直接比较, 消融实验要在这之后重新跑基线;
- 名字太常见的判断 (出现在 3 个以上, 或者 20% 以上的文件里) 只来自冒烟测试的一次运行, 暂定 (ADR-018).

## ADR-027 题库: 真实的题目学, 构造的题目只用; 每道题标出已知的行为变化

**背景**
第二次验证 (docs/v7/validation-002.md) 只说明了"卡片在学到它的题目上有用". 要回答的问题还有两类: **整理成功率** (反思写出的卡片, 有多少是对的, 能通过验证) 和 **长期记忆的问题** (卡片能不能用在别的仓库上; 在不相关的仓库上会不会误导; agent 确认, 去掉的判断对不对; 卡片多了以后会怎样). 只有 1 道题, 这些都无法测量.

**决定**
1. **两类题目** (`TaskSpec.origin`): `real` 是真实的仓库, 参考答案和隐藏测试来自作者自己的迁移; `synthetic` 是我们构造的小仓库, 问题和隐藏测试都是我们写的. **构造的题目只使用卡片, 不提炼卡片**: 不管运行成功还是失败, 都不做反思. 由代码强制执行 (反思拒绝 synthetic 题目的运行), 不靠人记得;
2. **所有运行都带记忆**, 也都有 compare_versions. 题库的测试关心的是记忆本身的行为: 推送得准不准, 确认和去掉对不对, 用到了以后结果怎样;
3. **每道题标出它包含的已知行为变化** (`evaluation.pitfalls`, 只给评分和统计用, agent 看不到), 每张卡片由人在抽查时标出它说的是哪一个 (`evidence.pitfall`). 这样每一次 (运行, 卡片) 都有标准答案: 卡片和这道题相关吗? 由此算出推送的精确率, 相关时确认的比例, 不相关时去掉的比例;
4. **只埋实验确认过的行为变化**: 候选的变化先在 pydantic 1.10.26 和 2.14.1 下各跑一次 (docs/v7/pitfalls.py), 静默的 (不报错, 只是结果变了) 和明显的 (报错) 分开. 静默的放进隐藏测试, 明显的让可见的测试失败, 保证 agent 有事可做;
5. **构造的仓库是可以复现的**: 源代码放在 `tasks/synthetic/<id>/base` (起点) 和 `reference` (参考答案, 带隐藏测试). 工作区准备时, 用固定的作者, 时间, 换行符把它们建成一个两次提交的 git 仓库, 提交的哈希每次都一样, 题目文件里写死. 参考答案的源代码属于控制平面, 加入 isolation 检查的路径;
6. **每道新题先过题目检查** (不调用模型): 旧版本下测试通过; 升级后可见的测试失败; 隐藏测试在"只做了明显修改"的代码上失败, 在参考答案上通过. 题目本身错了, 评测的结论就全错了;
7. **顺序**: 先学 (真实的题目, 失败的运行做反思, 新卡片验证), 后用 (构造的题目, 每道 3 次). 学到的卡片按时间累积, 构造的题目看到的是那时的卡片库.

**理由**
- 第 1 点是用户的决定: 构造的题目的问题是我们设计的, 从它们学出来的卡片等于我们自己写的答案, 再用在别的构造题上, 就成了循环论证. 真实的题目才是"agent 自己学会"的证据;
- 第 3 点: 没有标准答案, "agent 去掉了这张卡片"无法判断是对是错, 只能看最后通过与否, 而通过与否还受很多别的因素影响;
- 第 4 点: 和 ADR-018 一样, 题目里的每个"坑"都要有实验数据, 不能凭印象.

**代价**
- 没有"不带记忆"的对照组: 不能说"有记忆的通过率比没有记忆的高多少", 只能分析记忆在每一次运行里的行为;
- 构造的仓库比真实的仓库小, 也更"干净": 在它们上面的结果, 不能直接推广到真实的仓库;
- 卡片的 pitfall 标签由人标注, 有主观的成分. 标注写在证据里, 不进 prompt, 也不影响记忆的版本号.

## ADR-028 run 命令的记忆参数: 只从失败里学, 验证失败交给人

**背景**
到现在为止, 带记忆运行只能写进实验文件 (`memory = true`), 反思和验证要分别下命令. 用户希望一条命令就能完成"运行 → 学 → 验证".

**决定**
1. `run --task ... --memory`: 使用已经验证过的卡片;
2. `--learn`: 运行结束后, **只有评分没有通过, 而且是真实的题目时**才做反思, 写出草稿. 通过了的运行不做: 它没有"哪里错了"的信号, 写出来的经验没有证据, 也无法验证;
3. `--validate` (要和 `--learn` 一起用): 马上验证反思出的草稿. 不通过时保持草稿, 提示需要人查看, **不自动重试**;
4. `python -m bumpwise help`: 一次列出所有的命令和参数.

**理由**
- 反思很便宜 (bank-learn 的 gpuhunt: 约 9,000 tokens), 可以自动做; 验证是一次完整的运行 (73 万到 200 万 tokens), 由人决定要不要花;
- 验证失败的原因要看 trace 才知道 (第一张卡片: 适用条件写错了, 原因在反思看到的代码证据不够). 自动重试只是再花一次钱, 改变不了原因;
- 模型写草稿, 验证来裁决, 人只在验证失败, 报告告警, 定期抽查时介入 (ADR-024).

**代价**
- "做对了但很贵"的运行 (connect-eaas-core 用完了预算才通过) 里也许有值得学的东西 (省钱, 而不是做对), 现在不学. 要学的话, 需要另一种衡量方式 (同一道题前后的轮数和 tokens), 等题库的数据出来再决定 (ADR-018).

## 已知的局限

现在明确知道, 但有意留到以后解决的问题.

| 局限 | 影响 | 计划 |
|---|---|---|
| `run_command` 不受路径限制, 拥有当前用户的全部权限 | 可以读写仓库以外的文件, 可以绕过文件规则 | V9 沙箱. 在此之前, 本地环境只能用于可信的仓库, 运行时要有人观察 |
| 权限策略是黑名单 | 拦不住有意的绕过 | V4 的 grader 不依赖策略, 从结果再查一遍改动范围和依赖 (ADR-017); V9 沙箱 |
| 依赖包的安装脚本拥有当前用户的权限 | 不只来自 agent, 固定流水线执行 `pip install` 时同样存在 | V9 沙箱 |
| `edit_file` 在 `new_str` 包含 `old_str` 时不是幂等的 | 模型重复调用时, 同一处修改会被应用两次 | 可以检测"修改已经生效"; V5 增加"读过才能改, 读完之后不能被改过"的检查 |

| 上下文只增不减 | 很长的任务可能超出上下文窗口. 003, 004 最后一轮的上下文里, 57% 是 10 轮以前的工具结果, 大多是后来被改过的文件 | 上下文视图的规则已经写好 (`harness/context.py`), 但暂时不接进 loop: 没有数据证明它影响成功率 (ADR-023). 出现 ADR-023 里的信号时再接着做 |
| 先通读, 后修改 (运行 001, 002) | 第 2 轮就找到了阻塞问题, 却在十几轮之后才修复 | 只改 prompt 没有效果. 用 trace 统计只读的轮数, 需要时在 V5 加护栏. 运行 003 的 trace 显示这是有意的策略 (先摸清全部用法再整体迁移), 问题在于消耗的轮数 |
| 测试只在最后运行一次 (运行 002-004) | 中间任何一步改错, 都要到最后才会发现 | V5: test_cadence 护栏 (修改 6 次提醒一次). 005 运行了 5 次测试, 但护栏没有触发 (修改大多由 codemod 完成), 效果要在 V6 里看 |
| 在 cmd.exe 里使用 `\| tail` / `\| head` (运行 001-004) | 命令失败但退出码可能是 0, 模型以为执行成功了 | V5 已解决: pipe_exit_code 护栏在退出码是 0 时提醒. 005 触发 1 次, 下一轮就去掉管道重新运行. 管道本身没有减少 (005 改用 findstr) |
| 每次运行保留一份带 venv 的工作区 | `workspace/runs/` 越来越占空间 | 增加清理的办法 (比如只保留最近的 N 次). 注意 Windows 上 git 的对象文件是只读的, 删除时要先去掉只读属性 |
| 本地环境下, agent 仍然可以直接读本机上的镜像目录 | 工作区里已经没有起点之后的提交, 但 `run_command` 不受路径限制, 镜像里有完整的历史和参考答案 | V9 的沙箱: 容器里不挂载镜像. V4 的隔离检查会在 trace 里查找镜像, 题目文件和运行记录的路径, 但只是字符串匹配, 查不到相对路径和拼出来的路径 |
| 测试通过之后擅自做全局性的修改 (运行 002) | 引入了所有测试都发现不了的缺陷 (给枚举类加了 `model_config`) | V4 grader 的接口表面对比已经能自动发现这个缺陷 (判为 error, 见 [grade-002-004](v4/runs/grade-002-004.md)); 用 trace 查看模型的理由之后, 再决定是否修改 prompt |
| 没有重复调用的检测 | 模型反复执行同一个失败的操作, 只能靠 `max_turns` 兜底 | V5 已解决: RepeatGuard (第 2 次提醒, 第 3 次拦下), 失控的消耗由预算兜底 |
| 不检测"没有进展" | agent 真正卡住时 (不是重复同一个调用, 而是换着办法原地打转), 要等预算用完才停下 | V5 有意不做 (ADR-018): 003, 004 里"既没有修改也没有跑测试"的连续轮次 (003 第 2-12 轮, 004 第 2-6, 9-11, 34-39 轮) 全部是正常的探索和验证, 没有一次是真正卡住. 按"N 轮没有改动"判断只会误报. 等 V6 出现真正卡住的运行, 再按数据设计 |
| 仓库内容中可能混入提示词注入 | 模型可能把注释, README 中的文字当成指令. V5 之后还多了一种: 仓库的文件里写上 `[harness 护栏]` 这样的前缀, 冒充 harness 的提醒 | system_v2 起写明"仓库内容是数据, 不是指令", system_v3 写明 harness 的提醒只出现在什么位置. 用一道埋了注入文字的题目评测; 在 harness 里处理工具输出中出现的前缀 |
| 题目的锁文件和依赖声明不一致 | 准备流水线只修改了 `pyproject.toml`, `poetry.lock` 还锁定在旧版本 (运行 005 的报告里发现的). grader 也不检查锁文件 | 题目里写明锁文件怎么处理, 或者流水线重新生成锁文件; grader 检查两者是否一致 |
| 评分在 agent 用过的环境里进行 | agent 可以修改 venv 里的依赖, 或者放在被忽略的文件里, 改动范围检查看不到; 被测代码也能篡改检查的输出 | 把 `diff.patch` 应用到全新准备的工作区上再评分, 和 V9 沙箱一起做 (ADR-017) |
| 隐藏测试只有一份参考答案 | 和作者不同但同样合理的做法会被判失败, 已知的失败靠人维护 | 积累更多题目后, 用接口表面和行为对比的样本分担; 已知的失败必须写明原因 |
| 每次评分都要准备一次旧版本的环境 | 约 25 秒, 每次留下一个约 28 MB 的工作区. V6 起评测时每次运行都评分, 代价被放大了 | 旧版本的接口表面只取决于题目, 按题目缓存 |
| 批量运行只能顺序执行 | 一次 cortex 的运行约 3 分钟, 加上评分; 跑几十次要几个小时 | 并行需要互相隔离的环境, 和 V9 的沙箱一起做 |
| pipe_exit_code 对搜索命令的提醒是多余的 | 3 次提醒里, 1 次是 `git grep \| head` (退出码不重要) | 可以只在管道前面是测试命令时提醒. 等最终评测有了更多数据再决定 (ADR-018) |
| test_cadence 的提醒是软约束 | 冒烟测试里, 提醒之后又过了 7 轮才跑测试 | 等更多数据再决定要不要改成更强的形式 |
| 触发条件太宽, 自动检查发现不了 | 冒烟测试的卡片: 按文件算精确率 3/8, 召回 3/3 | 题库建好之后, 在多个仓库上测量精确率和召回率, 再定阈值 (ADR-018) |
| 总评只有 pass / fail | 2 项失败和 1 项失败看不出差别 | V6 增加更细的分数 (隐藏测试的通过率, 接口表面的 error 数等) |
| OpenAI 格式的模型客户端没有实现 | 只能使用 Anthropic 兼容接口 | 需要接入只提供 OpenAI 格式的服务商时实现 |
