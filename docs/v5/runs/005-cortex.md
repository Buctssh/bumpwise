## 最终报告的质量

报告的五个部分都有, 而且具体:
- 修改按类别列出 (RootModel, 字段默认值, ConfigDict, 废弃方法), 每一类都写了涉及的文件, 和 grader 看到的 16 个文件一致;
- 验证结果和 grader 的结论一致: 210 个测试通过, 源代码的废弃警告为 0, 静态搜索没有遗留;
- "需要人重点审核的地方"里的第 1 条 (`ActionStatuStr` 变成 RootModel), 正好是 grader 的接口表面对比给出的 2 条 warning;
- "没有解决的问题"里的 `poetry.lock`, 是题目和准备流水线的一个缺口: 依赖声明改成了 `>=2,<3`, 锁文件还是 1.10.12. grader 也没有检查锁文件.

漏掉的是 grader 发现的那一项: 带别名的字段用字段名赋值. 报告里的"行为检查"没有提到别名, 和 002-004 一样.

## 发现的问题

1. **escalate 的界线不清楚**: 模型把"很难判断哪一种行为是对的"理解成了"写进报告, 让人审核", 而不是"交给人". 两种做法的后果不同: 交给人会停下来等决定; 写进报告则是先按一种做法完成, 再请人审核. 对于这次的情况 (不改代码, 保持 v2 的默认行为), 写进报告其实是合理的. 要不要在 prompt 里区分这两种情况, 需要更多的运行数据;
2. **锁文件和依赖声明不一致**: 准备流水线只修改了 `pyproject.toml`. 以后的题目需要说明锁文件怎么处理 (题目里写明, 或者流水线重新生成锁文件), grader 也可以检查两者是否一致;
3. **agent 在虚拟环境里安装了额外的包**: 这是 ADR-017 里"评分在 agent 用过的环境里进行"这个漏洞的第一个真实例子. 这次装的是 codemod, 对结果没有影响; 但 grader 完全看不到它. 计划不变: V9 在全新的工作区上重放 diff 再评分;
4. **别名的问题第 4 次被漏掉**: 不是 agent 做事的方法有问题 (V5 已经让它跑了更多测试, 做了行为检查), 而是它不知道 pydantic 2 的这个行为变化. 这正是 V7 要验证的: 把 002-005 都漏掉的这一条经验写进记忆, 在另一道题上看它有没有用 (同一道题上验证, 就等于告诉了答案).
