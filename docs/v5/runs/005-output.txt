## 4. 需要人重点审核的地方

1. **`ActionStatuStr` 由 `BaseModel` 变成 `RootModel`**：这是 pydantic v2 强制的写法，但对外是可见变化——外部用户若写 `ActionStatuStr(__root__=...)` 或访问 `.data.__root__` 会失效，需改用 `ActionStatuStr(...)` / `.data.root`（`model_validate`/`model_dump` 也是新名字）。库内部没有任何地方使用 `__root__`，测试也不受影响。
2. **v2 的字符串字段不再宽松强转**：v1 允许把 int/float/bytes/bool 转成 `str`，v2 会报 `ValidationError`。本仓库模型里大量字段是 `Optional[str]`（例如 `AlertsDatum.contains_featured_host`、`Alert.alert_id`），如果真实 API 对这类字段返回数字/布尔，v1 能解析而 v2 会抛错。测试 fixture 覆盖不到这种情况；要保住旧行为就得引入自定义类型或改模型类型，属于业务决策，我没有动。
3. 同理，v2 默认启用了 smart union（v1 是按顺序尝试）。本仓库涉及的 union（`Union[List[str], Optional[str]]`、`Union[Optional[str], List[str]]`、`Optional[Union[int, Literal["Never"]]]`、`Optional[Union[IoCResponseItem, bool]]`）在现有输入下结果一致，但如果 API 返回同一值可匹配多个分支，结果可能与 v1 不同。
4. `from pydantic import ConfigDict, BaseModel` 的导入顺序是 codemod 生成的（未按字母序），不影响功能，为保持改动最小没有重排。
