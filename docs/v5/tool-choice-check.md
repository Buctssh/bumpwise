# 验证: DeepSeek 是否遵守 tool_choice: none

> V5 模块 3 的最后一轮要求模型只写报告, 不调用工具. 做法是请求里照常带上工具的定义 (历史里有 tool_use 时, 接口要求必须带上),
> 再传 `tool_choice: {"type": "none"}`. DeepSeek 的 Anthropic 兼容接口是否支持这个参数, 文档里查不到, 所以实际调用验证.
> 脚本: [check_tool_choice.py](check_tool_choice.py). 模型: `deepseek-anthropic` / `deepseek-flash`. 日期: 2026-10-20.

## 做法

任务是"依次读取 a.txt 和 b.txt, 每次只读一个, 读完之后总结". 先真实地请求一次, 模型调用 `read_file` 读 a.txt;
接上工具的结果之后, 正常情况下模型的下一步是去读 b.txt. 在这个时间点分别请求:

- 不能手工构造历史: DeepSeek 开着 thinking 模式, 要求历史里的 assistant 消息原样带上它自己的 thinking 块. 第一次尝试用手工构造的历史, 接口返回 400.

## 结果

| tool_choice | 有没有最后一轮的提醒 | 工具调用 | 回复 | 输入 tokens |
|---|---|---|---|---|
| auto | 没有 | 调用了 `read_file b.txt` | (对照组: 说明模型这时确实想调用工具) | 1253 |
| **none** | **没有** | 没有 | **把工具调用当成文字写了出来**: `<｜｜DSML｜｜ invoke name="read_file"> ... b.txt ...` | 149 |
| none | 有 | 没有 | 正常的最终报告 (完成了什么, 还剩什么没做) | 196 |
| auto | 有 | 没有 | 同样是正常的报告 | 1352 |

## 结论

- **接口层面支持 `tool_choice: none`**: 回复里没有 tool_use 块, 停止原因是 `end_turn`;
- **但只靠它不够**: 输入的 token 数从 1253 降到 149, 说明 none 时 DeepSeek 没有把工具的定义发给模型. 模型不知道工具已经不能用了,
  照样"调用", 只好把调用按内部的格式写成文字. 这种回复看起来是正常结束的, 如果出现在最后一轮, 最终报告就是一段乱码;
- **真正起作用的是提醒**: 带上"这是最后一轮, 不能调用工具, 请直接写最终报告"之后, none 和 auto 都写出了正常的报告;
- **loop 两样都用**: 提醒让模型知道该写报告, `none` 保证就算模型想调用工具也调用不了. 两层防护, 任何一层单独都不完全可靠.

## 留给以后

- 最后一轮的回复里出现 `<｜｜DSML｜｜` 这类内部格式时, 说明报告没有写出来. 现在不检测, 可以在 grader 或者 loop 里加一个检查,
  写进 trace (要不要做, 等运行 005 看最后一轮实际写出了什么, 按 ADR-018 用数据决定);
- 换别的服务商时, 要重新跑一次这个脚本: 不同的兼容接口对 tool_choice 的处理可能不一样.

## 调用的次数

一共 7 次请求: 第一次尝试 1 次 (400, 没有生成输出); 第二次尝试 3 次 (生成历史, auto, none); 加上提醒之后又 3 次 (生成历史, none, auto).
每次的输入在 1400 tokens 以内, 输出在 450 tokens 以内.
