# V7 反思的第一次真实检查: 冒烟测试的运行

ADR-024 规定: 反思写出的卡片是草稿, 不进入 agent 的上下文, 要经过验证才能升级. 这份记录是第一次在真实的运行上做反思, 检查这条规定是不是必要的, 以及反思本身有哪些问题.

- 运行: `runs/20261020-162442-cortex-xdr-client-pydantic2-6142` (V6 冒烟测试, 状态 budget, 评分 FAIL)
- 已知的真正原因: V0 第 6 轮, 在 v1 原代码上做实验确认过 (`docs/v0/cortex-xdr-client.md`). 3 个 `extra='allow'` 的模型, 用 Python 字段名赋值 (`Issue(insert_time=100)`), v1 能填进带别名的字段, v2 会当成额外字段, 带别名的字段还是 None. 修复是加上 `populate_by_name=True`. 002, 003, 004, 005, 冒烟测试, 一共 5 次运行都漏掉了这个问题.
- 反思的记录: `docs/v7/reflection-smoke-v2.json` (从运行目录复制出来, 因为 `/runs/` 不提交)

## 第一步: 重新评分

反思需要隐藏测试的报错, 而冒烟测试评分的时候, `grade.json` 还没有记录报错. 重新评分之后 (`failure_messages`), 报错显示导出的字典里, 键是 Python 字段名 (`insert_time`), 而不是别名 (`_insert_time`).

## 第二步: reflect_v1, 两个问题

1. **输出被截断了**: 默认的输出上限 8192 个 token (thinking 也算在里面), 模型写到一半就停了. 当时的代码没有检查 `stop_reason`, 只是报"解析不出 JSON". 原始输出也没有保存下来, 事后看不到它想说什么.
2. **原因猜错了**: 能读到的部分, 它的结论是"批量补 `= None` 默认值的时候, 不要丢掉 `Field` 里的 alias". 对照代码: 别名一直都在, 比如 `insert_time: Optional[int] = Field(None, alias='_insert_time')`. 它只看到了报错 (导出的键不是别名), 没有看到代码, 于是猜了一个最像的原因.

第 2 个问题正是 ADR-024 担心的情况: **如果草稿直接进入上下文, 以后的 agent 会被要求"检查别名有没有丢", 而它会发现别名都在, 然后把这条经验当成无关的东西去掉**. 草稿不使用, 必须验证, 这条规定是必要的.

## 第三步: 修改 (873ac04, fbb3648)

| 问题 | 修改 |
|---|---|
| 截断之后看不出原因 | 检查 `stop_reason == "max_tokens"`, 给出清楚的错误; 失败也写 `reflection.json` (原始输出 + 原因) |

| v1 的输出里写了 `status.progress`, `_insert_time` 这些别名 | 报错里带引号的名字也算原仓库的细节, 出现在卡片里会被退回 |
| 一次提炼 3 条, 往往是把一个问题拆碎了 | `MAX_CARDS = 2` |

## 第四步: reflect_v2 的结果

一张草稿, 自动检查全部通过, 没有退回:

- id: `pydantic2-config-alias-populate-by-name`
- 标题: 换成 ConfigDict 时丢了按字段名填充/别名配置
- 触发条件: `class\s+Config\b|allow_population_by_field_name|fields\s*=\s*\{|alias\s*=`

## 第五步: 人的抽查

逐个字段和 V0 实验确认过的事实对照:

| 字段 | 判断 | 说明 |
|---|---|---|
| `fix` | **正确** | `populate_by_name=True`, 2.11 起也可以用 `validate_by_name`. 和 V0 的修复, 作者的修复一致 |
| `symptom` | 基本正确 | "允许额外字段的模型会静默把值收进 extra" 和 V0 的实验一致 |
| `applies_when` | **条件写错了** | 它说 v1 用了 `allow_population_by_field_name` 或 `fields` 别名映射. 这个仓库两个都没有用, 原来的 Config 只有 `extra = 'allow'`. 真正的条件是"`extra='allow'` + 带别名的字段 + 用字段名赋值", 而它没有提到 `extra='allow'` |
| `why_tests_miss` | 不准确 | 它说"v1 里按字段名填充是默认放开的". v1 的默认值是 `allow_population_by_field_name = False`; 这个仓库在 v1 下能用字段名赋值, 是 V0 在 `extra='allow'` 的模型上实验看到的现象, 不是普遍的默认行为 |
| `trigger` | 太宽, 但没有漏 | 见下面的测量 |

触发条件的测量 (v1 的原代码, 34 个 .py 文件; 脚本在会话的临时目录里, 只是一次性的测量):

| 触发条件 | 匹配的文件 | 匹配的行 | 需要修复的 3 个文件 |
|---|---|---|---|
| 卡片的 | 8 | 24 | 3 个都匹配上了 |
| `extra\s*=\s*['"]allow\|Extra\.allow` (对照) | 3 | 3 | 3 个都匹配上了, 而且只有这 3 个 |

按文件算, 卡片的触发条件召回 3/3, 精确率 3/8. 在别的 pydantic v1 仓库上, `class Config` 和 `alias=` 几乎每个模型文件都有, 精确率会更低: 推送会变成噪声. 另外, 逐行的正则表达式写不出"同一个模型里既有 `extra='allow'` 又有别名"这种条件, 这是触发条件的格式本身的限制.

## 决定

**卡片保持草稿, 不由人修改, 直接去验证.** 理由:

1. 人的角色是监督, 不是生产 (ADR-024). 人改过的卡片, 验证的就不再是"反思能不能学会";
2. `applies_when` 的错误恰好是一个要测的风险: agent 看到"适用于用了 `allow_population_by_field_name` 的代码", 而这个仓库没有用, 它可能会把卡片去掉 (dismiss), 然后照样失败. 这正是报告里"去掉之后失败了"的告警要抓的情况. 验证的结果能告诉我们, 这类不准确的描述在实际中有没有害;
3. 如果验证没有通过, 而原因是 agent 去掉了卡片, 那就是 reflect_v3 的证据: `applies_when` 也要用代码核实 (现在只要求"原因"和代码一致).

| 缺口 | 处理 |
|---|---|
| 反思的 token 用量没有记录 | 已修: `reflection.json` 记录 `usage`. 题库的测试要算"提炼一张卡片的成本" |
| 在项目根目录运行 `pytest` 会收集到 `workspace/` 里目标仓库的测试 | 已修: `pytest.ini` 只收集 `tests/` |

| `applies_when` 和代码不一致, 自动检查发现不了 | 等验证的结果 (见上面的决定) |
