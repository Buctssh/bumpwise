# 通用升级流程（V0 归纳版）

本文根据 [gpuhunt](gpuhunt.md) 和 [cortex-xdr-client](cortex-xdr-client.md) 两次 pydantic v1 → v2 迁移的实际经验整理而成。

- 正文（第 1～9 节）是**通用流程**，不针对某一个仓库，也尽量不针对某一个库。
- 附录 A 是 **pydantic 专用的知识**，以后会变成 `skills/pydantic-v2/` 里的参考资料。
- 每一步都标出了以后由谁来做：**【代码】**表示由确定性的程序完成，**【agent】**表示需要模型判断。

---

## 0. 目标与原则

**目标：在“行为不变”的前提下，把依赖升级到目标版本，并产出一个方便人工审核的改动。**

1. **行为不变，而不是测试通过。** 测试通过只是必要条件。原有测试覆盖不到的地方，同样要保持和升级前一样的行为。
2. **改动最小。** 只改为了适配新版本所必需的地方，不顺手重构，不新增功能。
3. **不修改测试的断言含义。** 唯一允许的例外：把测试代码里的废弃写法换成新写法（比如 `parse_obj` → `model_validate`），并且断言的含义保持不变。
4. **不能确定时，停下来上报给人**，而不是猜。见第 8 节。
5. **能用代码确定的事情，就不交给模型。**

---

## 1. 准备环境 【代码】

1. 克隆仓库，切换到升级之前的提交，并**新建一个分支**再开始修改，避免处于 detached HEAD 状态。
   - 如果这个提交不在默认克隆的内容里（比如 PR 合并到的是功能分支），就单独 `git fetch origin <提交ID>`。
2. **为这个仓库单独创建虚拟环境**，不要和 agent 自己的环境混用。
3. 按照仓库自己的说明安装依赖，包括测试需要的可选依赖。
   - 项目用 poetry、uv 等工具管理依赖时，如果文档里提供了用 pip 安装的方法，可以优先用 pip，减少环境依赖。
4. **在本地忽略虚拟环境目录**：写进 `.git/info/exclude`，不要修改仓库的 `.gitignore`。否则 `.gitignore` 的改动会混进代码改动里。
5. 记录 Python 版本、依赖的当前版本。

## 2. 跑基线 【代码】

**在修改任何东西之前**，先把测试跑一遍，记录下来：

```shell
python -m pytest <测试目录> -q --continue-on-collection-errors
```

1. 记录通过、失败、收集错误的数量，以及每个失败和错误的原因。
2. 基线时就失败或者无法收集的测试（比如缺少可选依赖、和操作系统有关的问题），**之后都要排除在对比之外**，用 `--ignore` 保证升级前后跑的是同一批测试。
3. **保留一份可以随时运行的基线环境**：用 `git worktree add ../<仓库名>-base <升级前的提交>` 检出一份升级前的代码，单独建一个装旧版本依赖的虚拟环境。之后做新旧版本对比、在旧版本上复现问题时都要用到它。

## 3. 升级依赖 【代码】

1. 在虚拟环境里安装目标版本。
2. **修改依赖声明里的版本限制**，比如 `pyproject.toml`、`requirements.txt`。
3. **更新锁文件**，根据项目使用的工具选择正确的命令：`poetry lock`、`uv lock`、`pip-compile` 等。
4. 确认安装的确实是目标版本。

## 4. 第一次跑测试，先做分诊 【代码 + agent】

跑一次测试，**先判断失败属于哪一种**，再决定修改的顺序：

| 失败类型 | 怎么识别 | 影响范围 | 处理顺序 |
|---|---|---|---|
| **conftest 加载失败** | `ConftestImportFailure` | **全部测试都没有运行** | **第一优先**：它会挡住所有其他问题 |
| **包导入失败** | `ImportError`，或者在定义类的时候就报错 | 所有导入这个包的测试 | 第一优先 |
| 收集错误 | `ERROR collecting ...` | 一个测试文件 | 第二优先 |
| 测试失败 | `FAILED ...` | 一个测试 | 第三优先 |
| 废弃警告 | `DeprecationWarning` 等 | 现在不影响运行 | 最后处理 |

**重要**：如果第一次跑测试时“一个测试都没有运行”，那么无论之后做了多少修改，看到的结果都可能一样。先修好挡在最前面的那个错误。

## 5. 运行 codemod（如果目标库有官方的迁移工具） 【代码】

1. 先只预览、不修改（比如 `bump-pydantic --diff`），确认改动是合理的。
2. 正式执行。
3. 搜索工具留下的 TODO 提示（比如 `TODO[pydantic]`）。
4. 删除工具生成的临时文件（比如 bump-pydantic 生成的 `log.txt`）。
5. **把工具的修改单独提交一次**，提交信息写明是工具做的。
6. **不要因为工具没有留下 TODO，就认为它全部处理好了。** 在 cortex-xdr-client 里，它漏掉了 5 类问题，而且一个提示都没有。

## 6. 修复循环 【agent】

```
跑测试 → 按错误特征分组 → 选一组 → 定位原因 → 修改 → 重跑测试 → 下一组
```

1. **按错误特征分组**：异常类型 + 报错信息的模板。同一组错误通常只需要一种修改方法。
2. **每次只处理一组**，改完立刻重跑，确认这一组消失了，并且没有引入新的失败。
3. 修改之前，先理解原因：读报错信息、读相关的代码、读测试数据，必要时查阅迁移指南。
4. **拿不准新旧版本的行为差异时，写一个最小的实验脚本**，分别在新旧两个环境里运行，用结果说话。
5. 废弃警告**按来源区分**：来自源代码的要处理；来自测试文件自己代码的，不在这一阶段处理（见原则 3）。
6. 手工修改单独提交，和 codemod 的修改分开。

## 7. 三道检查：测试通过之后，还不能停 【代码 + agent】

只靠测试和警告，有两个盲区：**测试没有执行到的代码不会报警告**；**写法没有变、但行为变了的地方，既不会报警告，测试也发现不了**。所以测试全部通过之后，还要做三道检查。

### 第一道：测试和警告

- 原有测试全部通过（排除基线时就有问题的那些）。
- 来自源代码的废弃警告为 0。

### 第二道：静态扫描 【代码】

1. **搜索旧版本里所有已经废弃的写法**（清单见附录 A.1）。
2. **每个搜索结果都要确认对象的类型。** 文本搜索只能找到“长得像”的地方：
   - `response.json()` 是 requests 库的方法，不是 pydantic 的；
   - 项目自己定义的 dataclass 也可能有一个叫 `dict()` 的方法。
3. **结构性的检查用 AST 来做，不要用正则表达式。** 比如“类型允许 None、但没有默认值的字段”，正则表达式会漏掉 `Union[Optional[str], List[str]]` 这种嵌套写法。

### 第三道：行为检查

1. **对照迁移指南里的“行为变化”清单，逐条检查代码**（pydantic 的清单见附录 A.2）。
2. **做一次新旧版本对比测试**：把仓库里现有的测试数据、接口示例，或者真实数据，分别在第 2 步保留的基线环境和升级后的环境里解析一遍，逐字段比较结果。参考脚本：[diff_dump.py](diff_dump.py)。
   - 它不依赖任何人写的断言，能直接回答“同样的输入，新旧版本的输出是否一样”。
   - **真实数据最有价值**：gpuhunt 里的小数截断问题，就是只有真实数据才会暴露的。

## 8. 什么时候停下来，交给人 【agent】

遇到下面这些情况，**不要自己硬改**，停下来写一份诊断报告交给人：

| 情况 | 例子 |
|---|---|
| 要保持旧行为，就必须修改业务逻辑或者接口设计 | 新版本删除了某个功能，没有等价的替代写法 |
| 新旧版本的行为差异，很难判断哪一种才是对的 | 旧版本悄悄截断小数，到底是 bug 还是业务需要？ |
| 必须修改测试的断言，才能让测试通过 | 不属于“只是把废弃写法换成新写法” |
| 依赖之间互相冲突，无法同时满足 | 另一个依赖要求旧版本 |
| 同一个问题已经修改了好几轮，还是没有解决 | 达到了尝试次数的上限 |
| 需要提高 Python 的最低版本，或者需要提升这个库自己的主版本号 | 会影响这个库的所有使用者 |

诊断报告要写清楚三件事：**卡在了哪里、试过哪些办法、我认为可能的原因是什么。**

## 9. 验证和产出 【代码 + agent】

### 验证清单 【代码】

- [ ] 原有测试全部通过（排除基线时就有问题的那些）
- [ ] 来自源代码的废弃警告为 0
- [ ] 静态扫描：没有残留的旧写法
- [ ] 新旧版本对比测试：结果一致，或者每一处差异都有解释
- [ ] 依赖确实是目标版本；版本限制和锁文件都已经更新
- [ ] 没有修改测试文件，或者只是把测试里的废弃写法换成了新写法
- [ ] 没有新增 skip / xfail 标记，没有删除断言
- [ ] 改动里没有虚拟环境、日志、缓存这类无关的文件

### 提交 【代码】

按来源分开提交：工具的修改、手工的修改，必要时再按问题分开。

### PR 说明 【agent】

```markdown
## 升级了什么
<库名> 从 <旧版本> 升级到 <新版本>，原因：<安全漏洞 / 停止维护 / ……>

## 改了什么
- 由 <codemod 名称> 自动完成：<数量和类别>
- 手工修改：<按类别列出>

## 需要重点审核的地方
- <需要判断的修改，以及为什么这样改>

## 对使用者的影响
- <如果这是一个库：使用者需要修改的地方，比如方法改名、行为变化>
- <是否需要提升这个库自己的主版本号>

## 验证
- 测试：<通过数> / <总数>（排除了基线时就失败的 <N> 个，原因：……）
- 新旧版本对比：<示例数量>，结果 <一致 / 差异及解释>
```

## 附录 A：pydantic v1 → v2 专用知识

这一部分以后会变成 skill 里的 `references/`。

### A.1 写法改名对照表（机械替换）

| v1 | v2 |
|---|---|
| `Model.parse_obj(data)` | `Model.model_validate(data)` |
| `Model.parse_raw(json_text)` | `Model.model_validate_json(json_text)` |
| `obj.dict(...)` | `obj.model_dump(...)` |
| `obj.json(...)` | `obj.model_dump_json(...)` |
| `obj.copy()` | `obj.model_copy()` |
| `Model.__fields__` | `Model.model_fields` |
| `class Config: ...` | `model_config = ConfigDict(...)` |
| `allow_population_by_field_name = True` | `populate_by_name=True`（2.11 及以后推荐 `validate_by_name=True, validate_by_alias=True`） |
| `__root__: T` | 继承 `RootModel[T]`；读取时 `obj.__root__` → `obj.root` |
| `@validator` / `@root_validator` | `@field_validator` / `@model_validator` |

静态扫描用的正则表达式（结果要逐个确认对象的类型）：

```shell
rg -n "parse_obj|parse_raw|\.dict\(|\.json\(|\.copy\(|__fields__|class Config|__root__|@validator|@root_validator|TODO\[pydantic\]" <源代码目录>
```

### A.2 行为变化清单（需要判断）

| 变化 | v1 | v2 | 在哪里遇到过 | 处理方法 |
|---|---|---|---|---|
| **可空字段没有默认值** | `x: Optional[int]` 不传时默认为 None | **必须传** | 两个仓库都遇到了 | 补上 `= None`。**用 AST 扫描**，注意 `Union[Optional[...], ...]` 这类嵌套写法 |
| **小数转换成整数** | `81.6` 悄悄截断成 `81` | 报错 | gpuhunt（隐藏测试） | 如果需要保持旧行为，用 `BeforeValidator` 先截断 |
| **数字转换成字符串** | `123` 自动变成 `"123"` | 报错 | 作者的迁移说明里提到 | 检查接口数据里 ID 这类字段的实际类型 |
| **`extra='allow'` + 带别名的字段，用字段名赋值** | 填进带别名的字段 | 被当成额外字段，带别名的字段还是 None | cortex-xdr-client（隐藏测试） | 加上 `populate_by_name=True` |
| **根模型** | `__root__` 字段 | 定义类的时候就报错 | cortex-xdr-client | 改成 `RootModel` |
| **模型和字典比较** | `model == {...}` 可能为 True | 永远是 False | 作者的迁移说明里提到 | 如果代码里有这种比较，改成比较 `model_dump()` 的结果；PR 里要提醒使用者 |
| 联合类型的匹配方式 | 从左到右，第一个能转换成功的类型 | “智能模式”，优先选择类型完全匹配的那一个 | 两个仓库都没有遇到 | 检查同时包含 `int` 和 `str` 的联合类型 |

### A.3 bump-pydantic 已知会漏掉的问题

- `__root__` 根模型
- 嵌套写法的可空字段，比如 `Union[Optional[str], List[str]]`
- 不在模型文件里的方法调用，比如 API 文件里的 `Model.parse_obj(...)`、`obj.dict(...)`
- 依赖声明里的版本限制
- 而且**它不会为这些问题留下 TODO**

## 附录 B：错误特征速查

| 错误特征 | 可能的原因 | 处理方法 |
|---|---|---|
| `ConftestImportFailure` | conftest.py 导入了项目代码，而项目代码导入失败 | 看报错末尾，找到导入链中真正出错的那一行 |
| `To define root models, use pydantic.RootModel rather than a field called '__root__'` | v1 的根模型写法 | 改成 `RootModel`，见 A.1 |
| `Field required [type=missing]`，但这个字段的类型允许 None | 可空字段没有默认值 | 补上 `= None`，见 A.2 |
| `Input should be a valid integer, got a number with a fractional part` | 小数不能再转换成整数 | 见 A.2 |
| `PydanticDeprecatedSince20: Support for class-based config is deprecated` | `class Config` | 改成 `ConfigDict`，见 A.1 |
| `PydanticDeprecatedSince20: The parse_obj method is deprecated` | 方法改名 | 见 A.1；先看警告来自源代码还是测试文件 |
| `ModuleNotFoundError: No module named '<某个可选依赖>'` | 没有安装测试需要的可选依赖，和升级无关 | 在基线阶段就记录下来，并用 `--ignore` 排除 |
| 期望输出和实际输出只差一个换行 | 可能和操作系统有关 | 在基线上验证；以后在统一的 Linux 容器里运行 |

## 附录 C：操作清单 → V1 的工具

| 两次实践中用到的操作 | V1 的工具 | 工具需要具备的能力 |
|---|---|---|
| 跑测试 | `run_tests` | 支持排除文件；**分开报告** conftest 加载失败、收集错误、测试失败；按来源统计警告；输出要截断 |
| 搜索代码 | `search` | 底层用 ripgrep；限制返回条数 |
| 读代码 | `read_file` | 返回带行号的内容，支持只读一段 |
| 修改代码 | `edit_file` | 用“原文必须唯一匹配”的方式替换；**不改变文件原有的换行符** |
| 执行命令（查版本、导入检查、小实验、运行 ruff） | `run` | 带超时；明确指定虚拟环境里的 Python 路径 |
| 查阅迁移指南 | 先直接写进 prompt，V5 之后放进 skill | — |
| 跑基线、切换依赖版本、运行 codemod、新旧版本对比、AST 扫描 | V1 暂时由人或脚本完成，V3、V5 之后变成固定流程或工具 | — |

按照演进式开发的原则，**V1 只做前 5 个工具**。其余的等 V1、V2 的评测结果证明确实需要时再加。

## 附录 D：对评测的启示

1. **原有测试全部通过，会高估效果。** 两个仓库都是“原有测试全部通过”，但隐藏测试各自又发现了 1 处行为变化。
2. **隐藏测试的失败要再区分一次。** 参考答案里可能混有作者额外新增的功能。判断方法：在升级前的原代码上复现同样的场景；如果原来也不支持，就是新功能，不能算作 agent 的错误。**评测集里的每条隐藏测试都要标注它属于“迁移”还是“新功能”。**
3. **记录参考答案做了哪些超出迁移范围的事**：比如提高 Python 的最低版本、提升库的主版本号、新建基类，避免拿它当作“最小迁移”的标准答案。
