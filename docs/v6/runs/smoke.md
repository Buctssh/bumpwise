## 结论速览

- **流水线端到端走通**: 加载实验 → 批量运行 → 准备 → agent → 评分 → 清单 → 报告, 每一步都正常, 退出码 0;
- **harness 是干净的**: commit `8d2d8da`, `dirty: false`. 005 的 `dirty: true` 是因为终端输出写进了仓库, 这次写在仓库外面. 最终评测要的就是这样一个确定的版本;
- **预算的机制第一次全部用上**: 第 41 轮进入收尾 (81%), 第 45 轮是最后一轮, 一共用了 197.3 万 (预算的 98.7%), **没有超出**. 第 45 轮按 V5 的推算 (第 45 到 53 轮用完) 落在区间内;
- **最后一轮写出了正常的报告**: `tool_choice: none` 加上提醒, 回复里没有 DSML 那样的乱码 (V5 验证时, 只用 none 不加提醒就会出现);
- **没做完的运行也评了分**: 状态是 `budget`, 照样评分, 统计里是 fail 而不是 ungraded;
- **评分和 004, 005 一样是 FAIL**, 原因也一样: 别名 (`test_dotted_aliases_round_trip_without_data_loss`). 这是第 5 次.

## 和 005 对比

同样的题目, 模型, 配置 (system_v3, 3 个护栏, 200 万预算). 两次运行的差别:

| | 005 | 冒烟测试 |
|---|---|---|
| 停止方式 | finished (第 38 轮自己结束) | budget (第 45 轮, 最后一轮写报告) |
| token | 180 万 (90%) | 197 万 (99%) |
| 测试全部通过 | 第 24 轮 | 第 31 轮 |
| 跑测试的次数 | 5 | 6 |
| 批量修改的方式 | 官方的 codemod (bump-pydantic) | 自己写的 AST 脚本 (补了 456 处 `= None`) |
| 护栏提醒 | 1 次 (pipe_exit_code) | 3 次 (test_cadence 1 次, pipe_exit_code 2 次) |
| 评分 | FAIL (隐藏测试: 别名) | FAIL (隐藏测试: 别名) |

**同样的配置, 两次运行的过程差别不小**: 一次用了官方的 codemod, 一次自己写脚本; 一次在预算之内自己结束, 一次用到了最后一轮.
这再一次说明, 一次运行得不出可靠的结论 (003 的记录里第一次看到这一点). 评分的结论倒是很稳定: 5 次运行, 别名的问题 5 次都没有发现.

## 发现的问题

1. **pipe_exit_code 对搜索命令的提醒是多余的**: 到现在为止 3 次提醒里, 2 次是跑测试 (都在下一轮改正了), 1 次是 `git grep | head` (退出码不重要).
   可以改成只在管道前面是测试命令时提醒. 但只有 3 个数据点, 按 ADR-018, 等最终评测有了更多数据再决定;
2. **test_cadence 的提醒没有被马上执行**: 提醒是软约束, 模型可以不照做. 这次它在第 25-30 轮继续搜索和修改, 第 31 轮才跑测试.
   要不要改成更强的形式 (比如连续提醒, 或者拦下下一次修改), 同样要等更多数据;
3. **别名的问题第 5 次被漏掉**: 和 V5 的记录里的结论一样, 这是"不知道", 不是"做事方法的问题", 留给 V7.

## 对最终评测的启示

- 一次 cortex 的运行大约用 180 万到 200 万 tokens, 已经接近默认的预算. 最终评测要跑很多次, 这是主要的花费 (stats.py 的推算: 想分出 40% 和 80% 的差别, 每组大约要 11 次);
- 题库里应该有更小, 更便宜的题目: 一次运行便宜, 才能跑足够多的次数;
- 题目也应该覆盖"不知道就做不对"的情况 (比如别名), 这样 V7 的记忆才有可以衡量的效果.
