你负责从一次依赖迁移的结果里提炼可以复用的经验. 迁移由另一个 agent 完成, 之后由评分程序检查. 你会看到评分没有通过的检查 (包括 agent 当时看不到的隐藏测试和它们的报错), 报错里提到的名字在**迁移之前的代码**里所在的类的完整定义, 这些名字在迁移之后的代码里的样子, agent 的最终报告, 以及它调用过的工具的摘要.

# 提炼什么

只提炼能帮助以后的迁移做对的经验: **新旧版本之间的行为差异, 而这次的 agent 没有发现, 或者处理错了**. 每一条都必须有这次的失败作为证据.

- **先用给出的代码核实你的解释**: 你说的原因必须和代码一致. 比如代码里某个配置还在, 原因就不可能是"这个配置被删掉了". 只是猜测, 和代码对不上的原因, 不要写;
- **适用条件要能在迁移之前的代码里看到**: `applies_when` 里写的每一个条件 (某种配置, 某种写法), 都必须出现在"迁移之前的代码"里. 不要写代码里没有的配置. 以后的 agent 会拿你写的条件去对照它的代码, 条件写错了, 它会以为这条经验不适用;
- **写清楚旧版本下的实际行为**: 很多问题恰恰是旧版本有一个不明显的行为 (不一定是文档里的默认值), 新版本没有了. 以后的 agent 往往会凭记忆推断旧版本的行为, 写错了它就会被误导;
- 只有一次偶然的失误 (比如笔误), 或者和这个依赖无关的问题 (比如环境, 网络), 不要提炼;
- 没有值得提炼的经验时, 输出空的数组 [];
- 最多 2 条, 每个字段尽量简短 (一两句话);
- 已经有的经验不要重复提炼 (见最后).

# 写法的要求 (违反了会被自动退回)

1. **写库本身的行为, 不写这个仓库的细节**: 不能出现这个仓库的文件路径, 类名, 函数名, 字段名, 字段的别名, 测试数据里的值, 以及测试的名字. 需要举例时, 用通用的名字 (比如 `name`, `user_id`). 这条经验要能用在别的仓库上;
2. `trigger_pattern`: 一个 Python 的正则表达式, 用来在**别的仓库迁移之前的源代码**里, 逐行找出"可能受影响"的写法. 匹配真正的条件所在的那一行 (比如某个配置项), 而不是到处都有的写法: 匹配上的文件里, 大部分应该真的受影响. 写代码里能看到的现象, 不写结果 (比如"测试会失败"). 不要用嵌套的量词 (比如 `(a+)+`) 和反向引用. 实在找不到合适的写法时写 null;
3. `applies_when`: 一句话说明什么样的代码会受影响 (见上面: 条件要能在代码里看到);
4. `symptom`: 旧版本下是什么行为, 迁移之后变成了什么;
5. `why_tests_miss`: 为什么原有的测试发现不了;
6. `fix`: 怎样改. 如果要用到新版本才有的写法, 写明从哪个版本开始有;
7. `verify`: 一个最小的对比实验: 几行的自包含脚本 (自己定义需要的类, 不导入仓库的代码), 在旧版本和新版本下各运行一次 (agent 有 compare_versions 工具做这件事), 输出能直接看出两边的差别;
8. `id`: 小写字母, 数字和 -, 以依赖和版本开头, 例如 `pydantic2-alias-field-name`;
9. `title`: 一句话, 不超过 40 个字.

# 输出

只输出一个 JSON 数组, 不要输出其他文字:

```json
[{"id": "...", "title": "...", "applies_when": "...", "trigger_pattern": "...", "symptom": "...", "why_tests_miss": "...", "fix": "...", "verify": "..."}]
```
